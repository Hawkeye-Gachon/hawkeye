# 안내서 (GUIDE): 모델 구조, 읽는 순서, Android에 잇는 법

작성일 2026-11-14. 대상: 모델 `export/drowsiness_v0.onnx`(무작위 가중치)와 상수 묶음의 판 0. 다른 문서가 "spec v0"이라고
부르는 것이 이 판이다. 상수는 `feature_spec` 파일(모델 입력의 정의와, Kotlin으로 옮길 코드가 쓰는 상수를 담은 JSON. 이
문서에서는 "spec 파일"이라고 부른다)에 들어 있고 그 안의 `spec_version`이 0이다.

이 저장소는 운전자 졸음 판정 앱(Android, Kotlin)의 **모델 쪽**이다. 이 문서는 저장소를 처음 여는 사람이 가장 먼저 읽는
글이고 세 가지를 설명한다. (1) 모델의 구조, (2) 저장소·코드·문서가 어떻게 나뉘어 있고 어떤 순서로 읽으면 되는지,
(3) Android 앱에 어떻게 잇는지. 프로젝트 소유자는 0~5장과 7장을, Android 개발자는 0장, 1장, 2.1~2.2절, 3장, 4장, 5.5~5.6절,
6장, 7.2~7.4절을 먼저 읽으면 된다. 자기 얼굴로 직접 돌려 보려면 5.7절 "직접 실행해 보기"(녹화한 영상, Windows의 웹캠)로 간다.

> **보조 안내용이다. 안전 시스템이 아니다.** 여기서 나오는 이벤트와 확률은 운전자에게 주는 참고 신호다. 조용하다고 해서

## 1. 전체 흐름 한 장

먼저 낱말 넷. **MediaPipe Face Landmarker**는 구글의 공개 얼굴 분석 모델로, 영상 한 장에서 랜드마크(얼굴 위 점들의
좌표), 블렌드셰이프(눈 감김·입 벌림 같은 움직임을 수 하나로 나타낸 표정 계수), 얼굴 변환 행렬(머리의 방향을 담은 4x4
행렬)을 낸다. **ONNX**는 학습한 신경망을 담는 파일 형식이고 Android에서는 ONNX Runtime이 실행한다. **스텝**은 1초짜리 시간
칸이고, **창**은 모델에 한 번에 넣는 연속 120스텝이다.

```text
[앱]    카메라 프레임 (전면 카메라)
          │ 똑바로 세운다 · 좌우 반전하지 않는다 · 실제 시각(ms)을 타임스탬프로 준다
          ▼
[MP]    MediaPipe Face Landmarker (LIVE_STREAM 모드, 얼굴 1개)
          │ 랜드마크 · 블렌드셰이프 · 4x4 변환 행렬 · 타임스탬프
          ▼
[앱]    RawFrame 만들기 (얼굴이 없는 결과도 빠짐없이 만든다)
          ▼
[이식]  DriverPipeline.update(frame, speed_kmh)       ← 프레임마다 한 번
          │ ① 원시 신호      signals.compute         눈 뜬 정도(EAR), eyeBlink, 머리 각도, 입 벌림
          │ ② 기준선         BaselineEstimator       세션 앞 60~180초로 "이 운전자의 뜬 눈"을 한 번 잡는다
          │ ③ 프레임 상태    calibrate.frame_state   closure(눈 감김 정도 0~1), 기준 자세 대비 각도
          │ ④ 감김 구간      ClosureRunDetector      깜빡임·감김 하나하나의 시작, 길이, 속도
          │ ⑤ 스텝 특징      StepAggregator          1초마다 특징 17개
          │ ⑥ 모델 창        최근 120스텝이 다 차면 ──────▶ [ONNX] drowsiness_v{N}.onnx ──▶ 확률 3개
          │ ⑦ 규칙 엔진      RuleEngine              상태 이벤트 7종 (보정 중, 분석 불가, 시선 이탈, 졸음, 감김 …)
          │ ⑧ 경고 결정      AlertPolicy             이벤트 + 차량 속도 → 실제로 경고할 것
          ▼
[앱]    PipelineOutput을 받아 화면·소리·기록으로 쓴다
```

그림의 ①~⑧은 이 그림만의 번호다. 3.2절의 표와 SPEC 7.2절은 프레임을 버리는 검사와 시계를 1번, 2번으로 세고 묶는 법도
달라서 번호가 다르다.

| 표시 | 뜻 | 누가 만드나 | 정의된 곳 |
|------|----|-------------|-----------|
| `[앱]` | 앱 코드. 카메라, MediaPipe 호출, 차량 속도, 화면과 소리 | Android 팀 | 지킬 전제는 SPEC 1장 "앱이 보장해야 하는 것 (파이프라인을 부르기 전)" |
| `[MP]` | MediaPipe. 공개 표준 파일 `face_landmarker.task`를 그대로 쓴다 | 구글(저장소에 없다) | SPEC 0.1절 "앱이 받는 파일", README 3장 |
| `[이식]` | Python 참조 구현을 Kotlin으로 옮긴 코드. 모듈 일곱 개 | Android 팀이 SPEC을 보고 옮긴다 | SPEC 3~13장, `tests/vectors/` |
| `[ONNX]` | 모델 파일. 앱은 번들해서 실행만 한다 | 이 저장소가 내보낸다 | SPEC 14장 "ONNX 모델" |

이 그림에서 기억할 것 셋.

1. **모델은 영상도 랜드마크도 받지 않는다.** 모델에 들어가는 것은 그림의 ⑤가 만든 숫자 17개짜리 스텝 120개뿐이다.
2. **학습, 데모, 테스트 벡터가 같은 코드 한 벌을 쓴다.** 모두 `DriverPipeline`을 프레임 하나씩 부른다. 그래서 Kotlin으로
   옮긴 코드가 벡터와 맞으면 같은 `RawFrame`에 대해 학습 때와 같은 계산을 한다. 다만 같은 계산이 같은 입력을 뜻하지는
   않는다. 기기의 MediaPipe가 내는 값이 학습 추출과 같은지는 기기에서 확인하지 못했고(6.3절, 7.1절), 벡터가 모두
   통과해도 확인되지 않는 동작이 있으며(6.5절), 학습에 쓰는 기준선과 앱이 쓰는 기준선은 잡는 구간이 다르다(2.5절).
3. **모델 없이도 규칙은 돈다.** 마이크로슬립·수면·시선 이탈 규칙은 모델과 무관하고, 졸음도 지금은 PERCLOS 규칙이 판정한다.

## 2. 모델

### 2.1 입출력 계약

"계약"은 앱과 모델이 서로 지키기로 고정한 모양이다. 내보내기가 파일마다 검사한다(2.6절). 정의는 SPEC 14.1절 "입출력 계약".

| 항목 | 값 |
|------|----|
| 파일 | `export/drowsiness_v{N}.onnx`. 파일 하나, 1 MB 미만(`max_file_bytes` 1000000) |
| 형식 | ONNX opset 17, IR 8(연산자 묶음의 판과 파일 형식의 판). 연산자는 기본 도메인 `ai.onnx`뿐 |
| 입력 | 이름 `features`, float32 `[1, 120, 17]` = [배치 1, 스텝 120, 특징 17] |
| 입력의 순서 | `features[0][0]`이 **가장 오래된** 스텝, `features[0][119]`가 가장 최근 스텝. 특징의 순서는 3.5절의 # |
| 입력의 값 | 스텝 특징 **원시 값 그대로**. `Double`을 `Float`로 바꾸기만 한다 |
| 출력 | 이름 `probs`, float32 `[1, 3]` = (alert, low_vigilant, drowsy)의 확률. 합은 1. `probs[2]`가 졸음 확률 `p_drowsy` |
| 호출 | 스텝이 하나 나올 때마다, 최근 120스텝이 다 차 있으면 한 번(3.6절) |
| 메타데이터 | 파일 안에 적어 둔 이름-값 쌍 열 개이고 값은 모두 문자열이다: `model_version`, `feature_spec_hash`, `step_sec`, `window_steps`, `class_order`, `trained_on`, `commit`, `standardization`, `pipeline_hash`, `mediapipe_model_sha256`. v0의 값은 차례로 `0`, `f4031d09…`, `1`, `120`, `alert,low_vigilant,drowsy`, `none (random weights)`, `uncommitted-dirty`, `in_graph`, `650495e5…`, `64184e22…`다(이 문서를 고치며 v0 파일에서 직접 읽었다). 정의는 SPEC 14.3절 "메타데이터 (`metadata_props`, 값은 모두 문자열)", 앱이 비교하는 법은 6.2절 |

세 클래스는 학습 데이터(UTA-RLDD)의 라벨이다: alert(각성), low_vigilant(주의 저하), drowsy(졸음).

### 2.2 그래프 안에 든 것

파일에는 신경망만 들어 있지 않다. 앞뒤 처리가 모두 그래프(ONNX 파일에 담긴 계산 전체) 안에 있다(SPEC 14.2절 "그래프 안의
처리 (앱은 하지 않는다)").

```text
features [1,120,17]  (원시 값)
   │ ① log1p      특징 #9, #10, #11, #12, #14만:  x → log(max(x, 0) + 1)    횟수·길이처럼 꼬리가 긴 값을 누른다
   │ ② 표준화     (x − mean) / std                                        mean, std는 학습 데이터에서 구한 특징별 상수
   │ ③ 자르기     ±5 밖의 값은 ±5로 (z_clip)
   │ ④ 신경망     인과 TCN 또는 단방향 GRU → 점수(logits) 3개               2.3절
   │ ⑤ 온도       점수 / temperature                                      확률이 실제 빈도와 맞도록 맞춘 상수 하나
   │ ⑥ 소프트맥스 점수 3개를 합이 1인 확률로 바꾼다
   ▼
probs [1,3]
```

- **앱이 하면 안 되는 것**: 표준화, log1p, 소프트맥스, 온도 나누기. 한 번 더 표준화해도 오류가 나지 않으므로 주의한다. v0의
  상수(평균 0, 표준편차 1)로는 값도 그대로라 이 실수가 드러나지 않는다. 메타데이터 `standardization=in_graph`가 이를 선언한다.
- **앱(이식 코드)이 해야 하는 것 하나**: 넣기 전에 120 x 17 값이 모두 유한한지 본다. 하나라도 NaN이나 무한대면 추론을 건너뛰고
  센다(`nonfinite_windows`). 신경망 후보 가운데 하나인 GRU(2.3절)는 NaN 입력에도 그럴듯한 확률을 내기 때문이다. 이 검사는
  `DriverPipeline` 안에 있다.
- `mean`, `std`, `temperature`는 학습으로 정해져 버전마다 다르고, 같은 값이 `feature_spec_v{N}.json`에도 적힌다. v0은 0.0, 1.0,
  1.0이다(이 문서를 쓰며 v0 파일의 상수를 직접 읽어 확인했다).

### 2.3 신경망 후보 둘

코드는 `drowsy/models.py`다(이식 대상이 아니다). 둘 다 표준화된 `[1, 120, 17]`을 받아 점수 3개를 낸다. 어느 쪽을 내보낼지는
미리 정하지 않고 교차검증 안에서 고른다(2.5절).

**(가) 인과 TCN** (`CausalTCN`). TCN은 시간축으로 합성곱을 쌓은 신경망이다. "인과"는 어느 시점의 출력도 그 뒤의 입력을
보지 않는다는 뜻이고, 합성곱 앞에 0을 **왼쪽(과거 쪽)에만** 채워서 만든다. "확장"(dilation)은 합성곱이 입력을 몇 칸씩 건너뛰며
보는지다. 확장을 1, 2, 4, 8, 16으로 키우면 층이 적어도 먼 과거까지 본다. 기본 크기는 채널 32, 파라미터 30,915개다.
아래 그림의 낱말: 합성곱은 이웃한 스텝 몇 개(커널 3이면 셋)를 가중해 더하는 연산이고, 채널은 그 결과를 몇 벌 두는지다.
ReLU는 음수를 0으로 바꾸는 함수, 잔차 연결은 블록의 입력을 출력에 더하는 길, 선형 층은 값들을 가중해 더해 점수를 내는
마지막 층, 파라미터는 학습으로 정해지는 수다.

```text
z [1,120,17] ─ 축을 바꾼다 ─▶ [1,17,120]
   블록 1 (확장 1)    17 → 32 채널     블록 하나 = (왼쪽 0 채움 → 합성곱(커널 3) → 배치 정규화 → ReLU → 드롭아웃) 두 번
   블록 2 (확장 2)    32 → 32                    + 입력을 더하는 잔차 연결 → ReLU
   블록 3 (확장 4)    32 → 32          블록 1만 채널 수가 달라서 잔차 쪽에 1×1 합성곱을 둔다
   블록 4 (확장 8)    32 → 32
   블록 5 (확장 16)   32 → 32
   마지막 스텝(가장 최근 1초)의 값 32개만 읽는다
   선형 층 32 → 3  ─▶ 점수 3개
```

- 마지막 스텝이 볼 수 있는 과거의 길이(수용 영역)는 `1 + 2·(3−1)·(1+2+4+8+16)` = 125스텝이라 창 120스텝을 모두 덮는다.
- 배치 정규화(층의 출력을 고르게 맞추는 층)는 내보낼 때 합성곱에 합쳐지고, 드롭아웃(학습 때만 쓰는 무작위 끄기)은 사라진다.
  그래서 v0 파일에는 두 연산자가 없다.

**(나) 단방향 GRU** (`GRUClassifier`). GRU는 스텝을 오래된 것부터 하나씩 읽으며 기억(은닉 상태)을 갱신하는 순환 신경망이다.
기본 크기는 은닉 64, 파라미터 16,131개다.

```text
z [1,120,17] ─▶ GRU 1층 (은닉 64, 과거 → 현재 한 방향) ─▶ 마지막 은닉 상태 64개 ─▶ 드롭아웃 ─▶ 선형 층 64 → 3
```

탐색 범위는 미리 고정돼 있다(`config/default.yaml`의 `training.tcn`, `training.gru`): TCN은 채널 {16, 32} × 드롭아웃
{0.1, 0.3}, GRU는 은닉 {32, 64} × 드롭아웃 {0.1, 0.3}. 후보는 모두 여덟이다. 설계 근거는 PLAN 5.1절 "내보낼 후보".

### 2.4 v0이란

`export/drowsiness_v0.onnx`는 **기본 크기의 인과 TCN에 시드 0의 무작위 가중치를 넣고 학습 없이 내보낸 파일**이다(시드는
무작위 수의 출발값이다).

- 쓰임은 하나다. 앱 팀이 입출력 계약대로 연동을 시작하는 것. 출력 확률에는 뜻이 없고 판정에 쓸 수 없다.
- 메타데이터 `trained_on`은 `none (random weights)`다. 표준화 상수는 자리 채움 값이다(2.2절).
- 메타데이터 `commit`은 `uncommitted-dirty`다. 내보낼 때 저장소에 커밋이 없었기 때문이다. 첫 커밋 뒤에 v0을 다시 내보낼지는
  소유자의 결정을 기다린다. 다시 내보내면 파일의 크기와 sha256이 바뀌고 벡터 둘을 다시 만들어야 한다
  (`export/README.md`의 "v0 모델에 대해 알아 둘 것").
- 만든 명령과 파일별 해시는 `export/README.md`의 "파일", "어느 해시가 어느 파일과 짝인가"에 있다.

### 2.5 학습한 버전은 어떻게 고르고 내보내나 (설계. 실제 데이터로는 실행하지 않았다)

코드는 `drowsy/train.py`, `drowsy/evaluate.py`, `drowsy/export_onnx.py`에 있고 합성 데이터로 전 과정이 도는 것만 확인했다.
상세는 `docs/MODEL_CARD.md` 4장 "학습 절차 (설계. 실제 데이터로는 아직 실행하지 않았다)"와 PLAN 6장 "평가 절차"다.

1. **피험자 단위 교차검증.** 교차검증은 데이터를 여러 묶음(fold)으로 나눠 한 묶음씩 번갈아 시험에 쓰는 평가 방법이다.
   UTA-RLDD의 공식 5-fold(피험자 12명씩)를 쓴다. 한 사람의 영상이 학습과 시험에 함께 들어가지 않게 코드가 검사한다.
2. **안쪽에서 고른다.** 시험 fold를 뺀 나머지 4개 fold 안에서 다시 검증 fold를 돌려 가며 후보 여덟(TCN 넷, GRU 넷)의 점수를
   낸다. 점수는 macro-F1(세 클래스의 F1을 똑같은 무게로 평균한 값)이다. 평균이 가장 높은 후보를 찾고, 그 후보와의 차이가
   fold 간 표준편차 안인 후보들 가운데 **파라미터가 가장 적은 것**을 고른다(`train.choose`). TCN이냐 GRU냐는 여기서 정해진다.
3. **다시 학습해 한 번만 시험한다.** 고른 설정으로 학습 fold 전체(48명)를 시드 3개로 다시 학습하고 시험 fold를 한 번 평가한다.
   시험 fold는 선택, 조기 종료(검증 점수가 더 오르지 않으면 학습을 멈추는 것), 표준화 상수, 온도 어디에도 쓰지 않는다.
4. **최종 모델.** 같은 선택 절차를 60명 전체에 한 번 적용한 뒤 60명으로 학습한다(시드 0). 그래서 보고할 수치는 **같은 절차의
   교차검증 추정치이고 내보낸 파일 자체를 시험한 값이 아니다**(계획서의 결정 D10: 최종 모델과 보고 수치의 관계).
   명령은 `python -m drowsy.train --config config/local.yaml --run-name <이름> final`이다(README 4.10절 "최종 학습과 내보내기 (E4)").
   `config/local.yaml`은 실제 데이터의 경로를 적은 `config/default.yaml`의 사본이고 저장소에는 없다(git에 넣지 않는다).
   만드는 법은 README 4.0절 "실제 데이터를 쓸 때의 설정 파일 (`config/local.yaml`)"에 있다.
5. **내보내는 것.** `export/drowsiness_v1.onnx`와 `feature_spec_v1.json`(학습한 평균·표준편차·온도가 들어간다), 그 실행의
   `rules.json`. 최종 모델이 TCN이면 가중치를 8비트 정수로 줄인 INT8 파일 `drowsiness_v1_int8.onnx`도 만든다. GRU면 만들지
   않는다(계획서의 결정 D16: INT8 양자화는 TCN이 최종 모델일 때만).
6. **모델을 졸음 판정에 쓸지는 따로 가린다.** 교차검증 결과가 다섯 조건을 모두 채울 때만 규칙 엔진에서 졸음을 판정하는
   쪽(판정원. 4.3절)의 기본값을 모델로 바꾼다(계획서의 결정 D11: 학습 모델이 약할 때의 기본 동작). 조건은
   `config/default.yaml`의 `evaluation.model_gate`에 있다: macro-F1이 비교용 모델 LightGBM(같은 fold로 학습한 나무 기반
   분류기. 내보내지 않는다)의 값 − 0.02 이상, alert 대 drowsy 2클래스 영상 정확도 0.70 이상, alert 영상의 오경보 시간당
   2.0회 이하, 판정이 한 번이라도 난 alert 영상의 비율 0.10 이하, 판정이 난 drowsy 영상의 비율 0.50 이상.
   채우지 못하면 파일은 그대로 내보내되 "실험용"으로 남고 PERCLOS 규칙이 계속 판정한다. `train final`은 `rules.json`의
   판정원을 스스로 바꾸지 않는다. 사람이 바꾼다. 지금은 판정하지 않은 상태다(`docs/MODEL_CARD.md` 9장 "D11 판정 기준과
   '실험용'의 뜻").

내보낼 모델은 피험자의 alert 영상에서 잡은 기준선(그 사람이 눈을 뜨고 앞을 볼 때의 값. 3.3절)으로 정규화한 특징으로
학습한다(`training.export_arm: alert_baseline`). 앱은 그렇게 할 수 없고 그 세션의 앞 60초로 기준선을 잡는다. 그래서 같은
모델을 "앱 조건"(자기 세션 기준선 특징)으로도 평가하고, 위 6번의 판정은 그 값으로 한다(계획서의 결정 D1: 정규화 조건
셋의 비교).

## 3. 프레임에서 모델 입력까지

### 3.1 프레임 하나에 담겨야 하는 것

앱은 MediaPipe 결과 하나를 `RawFrame` 하나로 바꿔 파이프라인에 넣는다(SPEC 3.1절 "`RawFrame` (앱이 만든다)").

| 필드 | 형(Kotlin) | 내용 |
|------|-----------|------|
| `t_ms` | Long | 프레임 타임스탬프(ms). MediaPipe에 넘긴 값 그대로 |
| `face` | Boolean | 얼굴이 검출됐는지. 결과의 얼굴 목록이 비었는지로만 판정한다 |
| `w`, `h` | Int | MediaPipe에 넘긴(똑바로 세운 뒤의) 영상의 너비와 높이 |
| `lm` | Map<Int, (Double, Double)> | 랜드마크 번호 → 정규화 좌표 (x, y). 필요한 것은 44개(눈 윤곽 32, 홍채 10, 얼굴 폭 2) |
| `bs` | Map<String, Double> | 블렌드셰이프 이름 → 값. 필요한 것은 11개(`eyeBlinkLeft/Right`, `eyeLook*` 8개, `jawOpen`) |
| `m` | Double 16개 | 얼굴 변환 행렬. MediaPipe가 준 순서 그대로(열 우선: `M[i][j] = m[4*j + i]`) |

얼굴이 없으면 `lm`과 `bs`는 비어 있고 `m`은 길이 0이다. 번호와 이름의 표는 SPEC 4장 "인덱스 표"다.

### 3.2 프레임 하나의 처리 순서

`DriverPipeline.update(frame, speed_kmh)`가 하는 일이다. 번호는 SPEC 7.2절 "`update(frame, speed_kmh)`"의 번호를 따랐다.
`drowsy/pipeline.py` 머리말은 번호가 조금 다르다. SPEC의 1번과 2번을 1번 하나로 묶고, 4번을 3번(기준선)과 4번(프레임
상태)으로 나누고, 9번(돌려주기)을 따로 세지 않아 여덟 단계다. 5~8번은 양쪽이 같다.

| # | 하는 일 | 모듈 | 나오는 것 |
|---|---------|------|-----------|
| 1 | `t_ms`가 직전에 받은 프레임 이하이면 버리고 센다. `null`을 돌려준다 | `pipeline` | `dropped_frames` |
| 2 | 시계. 첫 프레임의 `t_ms`가 세션 원점이다. 직전 프레임과의 간격이 10초를 넘는지 본다 | `pipeline` | 세션 시간 |
| 3 | 원시 신호를 계산한다 | `signals` | `FrameSignals` |
| 4 | 기준선이 아직 없으면 추정기에 넣는다. 그다음 프레임 상태를 계산한다 | `calibrate` | `Baseline`(한 번), `FrameState` |
| 5 | 기준선이 있으면 특징용 감김 검출기와 스텝 누적기를 돌린다 | `blink`, `step_features` | `ClosureRun`(0~1개), `StepFeatures`(0개 이상) |
| 6 | 나온 스텝마다 모델 창에 넣고, 창이 찼으면 모델을 부르고, 그 스텝과 확률을 졸음 판정(`on_step`)에 넘긴다. PERCLOS 규칙은 스텝의 `perclos_60`을, 모델 규칙은 확률을 쓴다(4.3절) | `pipeline`, `rules` | 확률, `drowsy` 이벤트 |
| 7 | 이 프레임으로 나머지 규칙을 판정한다 | `rules` | 이벤트 |
| 8 | 이벤트와 차량 속도로 경고를 정한다 | `rules` | 경고 |
| 9 | 모아서 돌려준다 | `pipeline` | `PipelineOutput` |

원시 신호(3번) 가운데 알아 둘 것은 셋이다. 식은 SPEC 5장 "좌표, 각도, 좌우 규약과 원시 신호"에 있다.

- **EAR**(눈 가로세로비)과 **eyeBlink**: EAR은 눈꺼풀 위아래 점 사이의 거리를 눈 폭으로 나눈 값이고 **픽셀 좌표**로 계산한다.
  눈을 감으면 작아진다. eyeBlink는 MediaPipe가 주는 눈 감김 블렌드셰이프다. 뜬 눈에서도 0이 아니어서 기준선이 필요하다.
- **머리 각도**(yaw 좌우, pitch 위아래, roll 기울기): 변환 행렬에서 꺼낸다. 행렬을 행 우선으로 잘못 읽어도 오류가 나지 않고
  각도만 틀어지므로 주의한다.
- **좌우**: `_l`은 MediaPipe의 Left, `_r`은 Right다. 반전하지 않은 영상에서 운전자 자신의 왼쪽, 오른쪽이다.

### 3.3 기준선

눈 크기와 카메라 위치는 사람과 차마다 다르다. 그래서 세션 앞부분에서 "이 운전자가 눈을 뜨고 앞을 볼 때의 값"을 한 번
잡고(기준선), 그 뒤의 모든 신호를 그것에 대어 본다. 정의는 SPEC 8장 "기준선 (`BaselineEstimator`)".

- 잡는 것: 뜬 눈의 EAR(각 눈의 90 분위수. 작은 것부터 세어 90%째에 오는 값)과 eyeBlink(10 분위수), 기준 머리 자세, 입
  벌림과 눈동자 방향의 중앙값.
- 언제: 세션 시간 60초에 마감한다. 조건 셋(얼굴 프레임 300개 이상, 얼굴이 보인 시간 비율 0.5 이상, 두 눈의 기준 EAR이
  0.12~0.45)을 채우지 못하면 30초씩 늦춰 최대 180초까지 본다.
- 끝내 안 되면: 미리 정한 전역 상수로 대체한다(`fallback_global`). 이때는 기준 자세가 없으므로 시선 규칙이 세션 내내 꺼진다.
  앱이 이 결과를 읽는 법은 6.9절에 있다.
- 기준선이 잡히기 전: 전역 상수로 임시 계산한다(`provisional = true`). 감김 규칙이 임시 판정으로 돌고, 분석
  불가(`unable_to_analyze`)도 처음 10초가 지나면 판정하며 경고까지 나간다. 시선 규칙, 스텝, 모델은 아직 없다.
  README 맨 앞 표의 D4 행(계획서의 결정 D4: 기준선이 완성되기 전의 규칙 엔진)은 전에 이때 "감김 규칙만" 돈다고 적었지만,
  참조 구현은 분석 불가도 판정한다(README의 그 행은 2026-11-15에 고쳤다). SPEC 12.3절 "`unable_to_analyze`"의 의사 코드에
  보정 여부를 보는 조건이 없고, 이 문서를 고치며 얼굴 없는 프레임만 참조 구현에 넣었더니 세션 시간 10초에 `onset`과 경고가 났다(동작을 본 것이고 성능과는
  무관하다). 코드를 따른다.
- 전제: 세션을 시작할 때 운전자는 깨어 있고 앞을 본다. 처음부터 졸리거나 옆을 보고 있으면 기준이 틀어진다(README 6장
  "데이터에 대한 전제"의 1번).
- 기준선은 `DriverPipeline` 하나에 한 번만 잡는다. 운전을 새로 시작하면 `DriverPipeline`을 새로 만든다.

### 3.4 closure와 감김 구간

**closure**는 눈 감김 정도다. 0이 뜬 눈, 1이 감은 눈이다. EAR이 기준선에서 얼마나 줄었는지와 eyeBlink가 기준선에서 얼마나
올랐는지를 각각 0~1로 바꿔 반반 섞는다. 고개를 옆으로 돌리면 카메라에서 먼 쪽 눈이 부정확해지므로 그 눈의 비중을
줄이고(상대 yaw 15도부터 줄여 25도에서 0), 40도를 넘으면 closure를 "무효"로 둔다. 식은 SPEC 9장 "closure와 프레임 상태
(`calibrate.frame_state`)"에 있다.

**감김 구간**(`ClosureRun`)은 깜빡임이나 눈 감김 한 번이다. `ClosureRunDetector`가 closure에 히스테리시스(시작 문턱과 끝
문턱을 다르게 두어 문턱 근처에서 깜빡거리지 않게 하는 방법)를 걸어 찾는다. 같은 클래스를 문턱만 바꿔 **두 번** 쓴다.

| 쓰임 | 시작(이상) | 끝(미만) | 결과가 가는 곳 |
|------|-----------|----------|----------------|
| 특징용 | 0.5 | 0.3 | 스텝 특징 #4~#11 |
| 규칙용 | 0.7 | 0.5 | `microsleep`, `sleep` 이벤트 |

- 네 문턱은 실제 눈 감김으로 확인하지 못한 잠정값이다(7.2절, README 7장 "잠정 상수").
- 구간의 길이(`duration_ms`)는 closure가 시작 문턱 **이상이던 시간의 합**이다. 반쯤 뜬 채 머문 시간은 길이에 넣지 않는다
  (소유자 결정 1. 7.3절).
- 구간은 closure가 끝 문턱 아래로 내려가야 끝난다. 그래서 눈꺼풀이 두 문턱 사이에 머무는 동안에는 깜빡임 여러 번이 한
  구간으로 이어지고 길이가 쌓인다. 소유자가 그대로 두기로 정한 동작이고(소유자 결정 5) 알려진 한계다(7.2절).
- 유효한 프레임이 500 ms 넘게 끊기면 구간은 "잘린 구간"(`truncated`)으로 닫힌다.
- 알고리즘과 경계 사례는 SPEC 10장 "감김 구간 검출기 (`ClosureRunDetector`)"에 있다. 이식에서 가장 꼼꼼히 맞춰야 하는 곳이다.

### 3.5 스텝 특징 17개

1초마다 최근 60초(일부는 10초)를 요약한 숫자 17개가 나온다. 이 60초와 10초를 "조회 구간"이라고 부른다. 17개가 모델의
입력이다. 순서는 고정이고 정의는 SPEC 11.4절 "특징 17개 (순서 고정)"와 `config/feature_spec.json`의 `features`다.

| # | 이름 | 뜻 | 구간 | 단위 | 그래프 안 변환 |
|---|------|----|------|------|----------------|
| 0 | `perclos_60` | closure가 0.8 이상이던 시간의 비율(PERCLOS) | 60초 | 비율 | 없음 |
| 1 | `perclos_10` | 같음 | 10초 | 비율 | 없음 |
| 2 | `closure_mean_60` | closure의 시간 가중 평균 | 60초 | 0~1 | 없음 |
| 3 | `closure_mean_10` | 같음 | 10초 | 0~1 | 없음 |
| 4 | `blink_rate_60` | 깜빡임 수(분당) | 60초 | 회/분 | 없음 |
| 5 | `blink_dur_mean_60` | 깜빡임 길이의 평균(하나당 2000 ms까지만 친다) | 60초 | ms | 없음 |
| 6 | `blink_dur_std_60` | 깜빡임 길이의 표준편차 | 60초 | ms | 없음 |
| 7 | `closing_vel_mean_60` | 눈을 감는 속도의 평균 | 60초 | 1/s | 없음 |
| 8 | `opening_vel_mean_60` | 눈을 뜨는 속도의 평균 | 60초 | 1/s | 없음 |
| 9 | `long_closure_count_60` | 500 ms 이상 감은 횟수 | 60초 | 회 | log1p |
| 10 | `max_closure_ms_60` | 가장 길게 감은 시간(10000 ms까지만 친다) | 60초 | ms | log1p |
| 11 | `max_closure_ms_10` | 같음 | 10초 | ms | log1p |
| 12 | `yawn_count_60` | 하품 수(입 벌림이 2초 이어지면 한 번) | 60초 | 회 | log1p |
| 13 | `pitch_std_60` | 고개 위아래 각도의 흔들림 | 60초 | 도 | 없음 |
| 14 | `nod_count_60` | 고개 끄덕임 수(평소보다 10도 이상 숙였다가 0.2~3초 안에 돌아옴) | 60초 | 회 | log1p |
| 15 | `face_missing_ratio_60` | 얼굴이 보이지 않은 시간의 비율 | 60초 | 비율 | 없음 |
| 16 | `face_missing_ratio_10` | 같음 | 10초 | 비율 | 없음 |

- 계산할 수 없는 값은 0.0으로 둔다(NaN을 쓰지 않는다). 17개는 항상 유한하다.
- 모든 특징은 좌우를 바꿔도 값이 같은 양이다. 그래서 눈별 값은 들어가지 않는다(PLAN 3.2절 "모델 특징은 좌우 대칭").
  프레임률, 해상도, 머리 자세의 평균 수준처럼 녹화 조건을 직접 드러내는 값도 넣지 않았다(PLAN 4.6절 "스텝 특징 목록
  (F = 17, 순서 고정)").
- 하품과 끄덕임은 **특징으로만** 있다. 이벤트로는 나오지 않는다.
- PERCLOS의 감김 기준 0.8과 하품, 끄덕임의 기준은 잠정값이다(README 7장 "잠정 상수").
- #7, #8(속도)은 프레임률이 낮을수록 작게 읽힌다(SPEC 17.1절 "프레임률에 따라 달라지는 것").

### 3.6 시간: 스텝, 창, 첫 모델 출력

- **세션 시간** = `t_ms` − 첫 프레임의 `t_ms`. **스텝 k**는 세션 시간 `[1000(k−1), 1000k)` ms를 대표하고, 세션 시간이 `1000k`
  이상인 첫 프레임이 도착했을 때 나온다.
- **유지 규칙**: 한 프레임의 상태는 다음 프레임까지 이어진 것으로 보되 최대 200 ms까지만이다. 넘는 부분은 "데이터 없음"이고
  얼굴이 없는 시간과 똑같이 친다. 비율은 모두 프레임 수가 아니라 **시간**으로 계산한다(SPEC 6장 "타임스탬프, 세션 시간, 유지 규칙").
- **`full_lookback`**: 60초 조회 구간이 다 찬 스텝에 붙는 표시다. 이 스텝만 모델 창과 PERCLOS 졸음 판정에 쓰인다.
- **모델 창**: 번호가 이어진 `full_lookback` 스텝 120개. 덜 찬 스텝이나 번호가 건너뛴 스텝을 만나면 창을 비운다.

아래는 기준선이 60초에 잡힌 경우의 시간표다. 뼈대는 SPEC 11.7절 "세션 시간 흐름 (`T_b` = 기준선 완성 시각)"의 표이고,
스텝과 모델의 시각은 벡터 `e2e_250s`로 확인했다. 분석 불가의 줄은 그 표에 없고 SPEC 12.3절 "`unable_to_analyze`"에서
왔다(3.3절).

```text
세션 시간
    0 s  |  기준선 수집(보정 중). 스텝은 아직 없다. 감김 규칙은 첫 프레임부터 임시 판정으로 돌고, 분석 불가는 10초부터 판정한다
   60 s  |  기준선 완성. 시선 규칙이 돌기 시작한다. 스텝 61부터 나오고 60초 조회 구간을 채운다
  120 s  |  스텝 120부터 full_lookback. PERCLOS 졸음 판정이 이 스텝들을 쓴다
  239 s  v  스텝 239에서 첫 모델 호출. 그 뒤로 1초마다 확률 하나
```

- 첫 확률은 **세션 시작 239초 뒤**에 나온다(기준선 60초 + 조회 구간 60초 + 창 120스텝. 스텝 120이 조회 구간이 다 찬 첫
  스텝이고 거기서부터 120개째가 스텝 239다). 기준선이 180초까지 늦어지면 스텝 359다(참조 구현에 얼굴 없는 프레임만 넣어 확인한
  값이고 성능과는 무관하다. 다른 문서의 표현은 "최대 약 6분").
- 프레임이 10초 **이하**로 끊기면 그 사이의 스텝을 다음 프레임에서 한꺼번에 내고 스텝마다 모델을 부른다(한 프레임에 최대
  10번. 소유자 결정 3).
- 프레임이 10초를 **넘게** 끊기면 검출기, 누적기, 모델 창, 규칙 엔진이 다시 시작한다(규칙 엔진의 다시 시작이 소유자 결정
  4다). 기준선은 남는다. 모델 창이 다시 차려면 179초가 걸린다(SPEC 12.7절 "10초 초과 끊김 (`reset_after_gap`)"). 끊김의
  길이에 따라 일어나는 일은 SPEC 17.2절 "프레임 간격이 길어질 때 (상수에서 나오는 값)"의 표 하나에 모여 있다.

## 4. 규칙과 경고

### 4.1 `update`가 돌려주는 것

`PipelineOutput` 하나다(SPEC 3.8절 "`PipelineOutput` (`DriverPipeline.update`의 출력, 7장)"). 버린 프레임에서는 `null`이다.

| 필드 | 내용 | 앱에서의 쓰임 |
|------|------|---------------|
| `state` | 이 프레임의 `FrameState`(closure, 얼굴 유무, 상대 각도 등) | 디버그 화면, 기록 |
| `runs` | 이 프레임에서 끝난 특징용 감김 구간. 0개 또는 1개 | 기록 |
| `steps` | 이 프레임이 내게 한 스텝들. 보통 0개, 1초에 한 번 1개 | 기록 |
| `step_probs` | `steps`와 길이가 같다. 그 스텝에서 모델을 불렀으면 확률 3개, 아니면 `null` | 기록, 표시 |
| `probs` | `step_probs`의 마지막 원소. 스텝이 없으면 `null` | 표시 |
| `events` | 이 프레임에서 난 **상태 이벤트**. 속도와 무관하게 모두 나온다 | 상태 표시, 기록 |
| `alerts` | **실제로 경고할 이벤트**. 우선순위 순서 | 소리, 화면 경고 |

이벤트와 경고는 같은 자료형 `DriverStateEvent`다(SPEC 3.7절 "`DriverStateEvent` (12장)"). 필드는 `type`(종류),
`severity`(0~3), `t_start_ms`(상태가 시작된 시각), `duration_ms`, `confidence`(그 구간에서 신호가 유효했던 시간의 비율. `drowsy`만
다르다: 모델이 판정했으면 그 스텝의 `p_drowsy`, PERCLOS 규칙이 판정했으면 `1 − face_missing_ratio_60`이다. SPEC 12.9절
"`confidence`"), `source`(근거 신호), `phase`(`onset` = 시작, `end` = 끝), `provisional`(기준선이 잡히기 전의 프레임이 낸
이벤트인지)이다.

### 4.2 이벤트 종류

일곱 가지다. 상태가 시작될 때 `onset`, 끝날 때 `end`가 난다. 예외는 하나다. `sleep`까지 간 감김에서는 `microsleep`의 `end`가
따로 나지 않고 `sleep`의 `end` 하나만 난다(표 아래 둘째 항목). 정의는 SPEC 12.8절 "이벤트 표", 값은 `export/rules.json`이다.

| `type` | 언제 시작하나 | 심각도 | 재경고 대기 | 이 속도 미만이면 경고 안 함 |
|--------|---------------|--------|-------------|-----------------------------|
| `calibrating` (보정 중) | 첫 프레임부터 기준선이 잡힐 때까지 | 0 | 없음 | 경고하지 않는 종류 |
| `unable_to_analyze` (분석 불가) | 최근 10초 가운데 얼굴이 보인 시간이 절반 미만 | 1 | 30초 | 억제 없음 |
| `gaze_away_long` (장시간 시선 이탈) | 전방 주시 영역 밖이 연속 3초 이상 | 2 | 10초 | 20 km/h |
| `vats` (시선 이탈 누적) | 최근 30초 가운데 영역 밖 시간의 합이 10초 이상 | 2 | 30초 | 20 km/h |
| `drowsy` (졸음) | PERCLOS 규칙 또는 모델 규칙(4.3절) | 2 | 300초 | 50 km/h |
| `microsleep` (마이크로슬립) | 한 번의 감김에서 closure 0.7 이상이던 시간이 1초 이상 | 3 | 5초 | 20 km/h |
| `sleep` (수면) | 같은 감김이 3초 이상 | 3 | 없음, 3초마다 되풀이 | 20 km/h |

- "전방 주시 영역"은 기준 자세에서 좌우 23도, 위 25도, 아래 18도 안이다. 눈동자만 돌린 경우를 잡는 보조 조건도 있다. 이 값들은
  공개 근거가 없는 잠정값이다(SPEC 12.4절 "전방 주시, `gaze_away_long`, `vats`").
- 한 번의 감김은 `microsleep` 시작, `sleep` 시작, 그리고 도달한 가장 높은 종류의 `end` 하나를 낸다. 분석 불가인 동안에는
  시선과 감김 규칙이 멈춘다.
- 한 프레임 안에서 이벤트가 나오는 순서는 SPEC 7.3절 "한 프레임 안의 이벤트 순서"에 고정돼 있다.

### 4.3 모델의 확률이 쓰이는 곳

- 확률을 쓰는 곳은 `drowsy` 이벤트 하나뿐이다. 다른 여섯 종류는 모델과 무관하다.
- 누가 판정하는지는 `rules.json`의 `drowsiness.source`가 정한다: `perclos`(지금 값), `model`, `either`(둘 중 하나라도 켜지면 졸음).
- **PERCLOS 규칙**: `perclos_60`이 0.15 이상인 스텝이 10개 연속이면 시작, 0.10 미만인 스텝이 10개 연속이면 끝(두 임계값은 잠정).
- **모델 규칙**: `p_drowsy`가 0.6 이상인 스텝이 10개 연속이면 시작, 0.4 이하인 스텝이 10개 연속이면 끝. 끝난 뒤 60초 동안은 다시
  시작하지 않는다.
- 확률을 평균하거나 매끄럽게 하는 처리는 없다. 연속 스텝 수를 세는 것이 유일한 시간 필터다(SPEC 12.6절 "`drowsy` (`on_step`)").
- 모델은 `source`가 무엇이든 창이 차면 불린다. `source: perclos`인 지금은 확률이 `probs`로 나오기만 하고 이벤트를 만들지 않는다.
  v0의 확률은 무작위 가중치의 출력이므로 화면에 뜻 있는 값처럼 보여 주지 않는다.

### 4.4 경고 결정

`AlertPolicy`가 이벤트 가운데 실제로 운전자에게 알릴 것을 고른다(SPEC 13장 "경고 결정 (`AlertPolicy`)").

- 경고가 되는 것은 `onset`뿐이다. `end`는 상태가 끝났다는 것만 알린다. `calibrating`은 경고하지 않는다.
- **재경고 대기**: 같은 종류의 경고를 낸 뒤 4.2절 표의 시간 안에 그 종류의 상태가 **새로 시작되면** 바로 경고하지 않는다.
  이어지고 있는 상태를 그 시간마다 다시 경고한다는 뜻이 아니다. 졸음 상태가 한 시간 이어져도 경고는 한 번이다(상태가
  이어지는 동안 다시 경고하는 것은 아래의 `sleep`뿐이다).
- **속도 억제**: 차량 속도가 표의 값 미만이면 경고를 내지 않는다. 상태 이벤트(`events`)는 그대로 나온다.
- **미뤄 둔 경고**(소유자 결정 2): 대기나 속도에 막힌 `onset`은 종류별로 하나 보관한다. 막힘이 풀렸을 때 그 상태가 아직
  이어지고 있으면 한 번 경고하고, 그전에 상태가 끝나면 버린다. 한 `onset`은 한 번만 경고된다.
- **되풀이**: `sleep`만 상태가 이어지는 동안 3초마다 다시 경고한다.
- **순서**: `alerts`는 우선순위(`sleep`, `microsleep`, `gaze_away_long`, `vats`, `drowsy`, `unable_to_analyze`) 순이다. 한 번에
  여러 개가 나올 수 있고, 앱은 첫 원소를 대표로 쓰면 된다.
- 심각도, 재경고 대기, 되풀이 주기는 공개 근거가 없는 설계값이다. 속도 기준은 Euro NCAP 2026의 값이다(`config/rules.yaml`의 주석).

### 4.5 차량 속도

`update`의 둘째 인자 `speed_kmh`다. 단위는 **km/h**, 형은 `Double`, 모르면 `null`이다. 속도는 경고(`alerts`)에만 영향을 준다.
이벤트, 특징, 모델 입력에는 들어가지 않는다. 앱에서 넘기는 법은 6.8절에 있다.

### 5.2 파이프라인을 지나는 자료형

모두 불변 값이고 `drowsy/types.py`에 있다(SPEC 3장 "자료형").

```text
RawFrame                         --signals.compute-->        FrameSignals
FrameSignals + Baseline          --calibrate.frame_state-->  FrameState
FrameState                       --ClosureRunDetector-->     ClosureRun
FrameState + ClosureRun          --StepAggregator-->         StepFeatures
StepFeatures x 120               --model (ONNX)-->           probs
FrameState, StepFeatures, probs  --RuleEngine-->             DriverStateEvent (이벤트)
events + speed_kmh               --AlertPolicy-->            DriverStateEvent (경고)
```

| 자료형 | 한 줄 | 얼마나 자주 | SPEC |
|--------|-------|-------------|------|
| `RawFrame` | MediaPipe 결과 하나 | 프레임마다 | 3.1절 |
| `FrameSignals` | EAR, eyeBlink, 머리 각도 등 원시 신호 | 프레임마다 | 3.2절 |
| `Baseline` | 이 운전자의 기준값 | 세션에 한 번 | 3.3절 |
| `FrameState` | closure, 상대 각도, 유효 표시 | 프레임마다 | 3.4절 |
| `ClosureRun` | 감김 구간 하나(시작, 끝, 길이, 진폭, 속도) | 감김이 끝날 때 | 3.5절 |
| `StepFeatures` | 스텝 번호 `k`, 끝 시각, `full_lookback`, 값 17개 | 1초마다 | 3.6절 |
| `DriverStateEvent` | 상태 이벤트. 경고도 같은 형이다 | 상태가 바뀔 때 | 3.7절 |
| `PipelineOutput` | `update` 한 번의 결과 묶음 | 프레임마다 | 3.8절 |

### 5.7 직접 실행해 보기

자기 얼굴로 파이프라인을 돌려 보는 길이 둘 있다. 녹화한 영상 파일을 한 번에 돌리는 것(가)과, Windows에 붙은 웹캠으로
실시간으로 돌리는 것(나)이다. 둘 다 저장소 루트에서 실행하고, MediaPipe 모델 파일 `models/face_landmarker.task`가 있어야
한다(README 3장 "환경 준비"). 두 명령 모두 얼굴이 나온 화소를 디스크에 쓰지 않는다(계획서의 결정 D13). 남는 것은 랜드마크
값의 표, 타임라인 그림, 이벤트 JSON이다. 모델은 v0(무작위 가중치)이므로 모델의 확률에는 뜻이 없고, 뜻이 있는 것은 규칙이 낸
이벤트뿐이다(2.4절).

**(가) 녹화한 영상 파일: `python -m drowsy.demo --video`**

1. 얼굴을 정면에서 찍은 영상을 저장소의 `videos/` 폴더에 둔다. 이 폴더와 영상 확장자(`.mp4` 등)는 git이 무시하도록 정해져
   있어서(`.gitignore`) 실수로 커밋되지 않는다.
2. 아래 명령을 실행한다. 결과는 `out/demo/<파일 이름>_timeline.png`(가로축을 맞춘 네 줄: closure, 전방 주시, 모델 출력,
   이벤트)와 `out/demo/<파일 이름>_events.json`이다(README 4.12절 "데모").
   ```
   python -m drowsy.demo --video videos/<파일 이름>.mp4
   ```
   출력의 첫 줄은 영상을 어느 각도로 세웠는지다(회전 자동 점검). 점검이 가르지 못했다고 나오거나 각도가 틀렸으면
   `--rotation 90`처럼 세우는 각도(반시계)를 직접 준다. 얼굴이 없는 600프레임 시험 영상에서 이 명령은 6.0초 걸렸다
   (2026-11-14, 이 PC. 얼굴이 있는 영상에서는 재지 않았다).
3. 찍는 법. **처음 60초는 기준선이다**(3.3절): 눈을 평소처럼 뜨고 앞을 본다. 얼굴이 충분히 보이지 않으면 기준선은 30초씩
   180초까지 늦어진다. 기준선이 잡히기 전에는 감김 이벤트가 임시 판정(`provisional`)으로만 나고 옆을 봐도 시선 이벤트가 나지
   않으므로, 아래 동작은 60초가 지난 뒤에 한다. 동작 사이에는 몇 초씩 앞을 본다.

| 동작 (60초 뒤) | 나올 이벤트 | 규칙의 조건 (`config/rules.yaml`의 값) |
|----------------|-------------|----------------------------------------|
| 눈을 1초 이상 감는다 | `microsleep` | 한 번의 감김에서 closure가 0.7 이상이던 시간이 1초(`closure.microsleep_ms: 1000`). 감김은 closure가 0.5 아래로 내려가야 끝난다 |
| 눈을 3초 이상 감는다 | `microsleep`, 이어서 `sleep` | 같은 감김이 3초(`closure.sleep_ms: 3000`). 감고 있는 동안 `sleep` 경고가 3초마다 되풀이된다 |
| 고개를 돌려 3초 이상 옆을 본다 | `gaze_away_long` | 전방 주시 영역(기준 자세에서 좌우 23도, 위 25도, 아래 18도 안. 눈동자 방향의 보조 조건도 있다. 4.2절) 밖이 연속 3초(`gaze_away_long.onset_ms: 3000`) |
| 3초가 안 되게 옆을 보고 앞을 보기를 되풀이해, 30초 안에 옆을 본 시간이 모두 10초가 되게 한다(예: 2초 옆, 2초 앞) | `vats` | 최근 30초 가운데 영역 밖 시간의 합이 10초(`vats.window_ms: 30000`, `cumulative_ms: 10000`) |
| 카메라를 손으로 가린다 | `unable_to_analyze` | 최근 10초 가운데 얼굴이 보인 시간이 절반 미만(`unable_to_analyze.window_ms: 10000`, `min_face_ratio: 0.5`). 그 전까지 얼굴이 보였다면 5초 넘게 가려야 하고, 손을 뗀 뒤에는 얼굴이 다시 보인 시간이 절반을 넘어야 끝난다. 세션의 처음 10초에는 판정하지 않는다 |
| (오래 걸린다) 눈을 자주, 길게 감는다 | `drowsy` | 최근 60초 가운데 closure가 0.8 이상이던 시간이 15%(9초) 이상인 스텝이 10개 이어짐(`drowsiness.perclos.onset_ratio: 0.15`, `onset_steps: 10`). 60초 조회 구간이 다 찬 스텝만 쓰므로, 기준선이 60초에 잡히면 세션 120초부터 센다(3.6절) |

- 이 표는 **규칙에 적힌 조건이지 실제 얼굴로 확인한 결과가 아니다.** closure의 문턱(0.5, 0.7, 0.8)과 전방 주시 영역의 각도는
  실제 눈과 시선으로 확인하지 못한 잠정값이다(7.2절). 그래서 눈을 감아도 closure가 0.7에 못 미치면 `microsleep`이 나지 않을 수
  있고, 그것만으로 도구가 틀렸다고 볼 수는 없다. 이 저장소에서 영상으로 돌린 것은 얼굴이 없는 시험 영상과 공개 사진 두 장으로
  만든 짧은 클립뿐이다(README 2장 "지금 상태 (2026-11-15)"의 M3 행).
- 분석 불가(`unable_to_analyze`)인 동안에는 감김과 시선 규칙이 멈춘다(4.2절). 가린 직후의 동작은 이벤트를 내지 않는다.
- 이벤트(`events`)와 경고(`alerts`)는 다르다(4.1절, 4.4절). 같은 종류의 경고는 재경고 대기 동안 다시 나지 않는다(예:
  `microsleep` 5초). `--speed-kmh`를 주지 않았으므로 속도로 억제되는 경고는 없다.
- 모델 줄은 세션 239초가 지나야 점이 찍히고(3.6절), 찍혀도 무작위 가중치의 출력이다.
- 같은 영상을 여러 번 볼 때는 한 번 추출해 두고 `--raw`로 돌리면 MediaPipe를 다시 돌리지 않는다(README 4.12절).

**(나) Windows의 웹캠으로 실시간: `python -m drowsy.live`**

저장소는 WSL2(Windows 안에서 도는 Linux) 안에 있고, WSL에서는 Windows의 카메라가 보이지 않는다. 그래서 Windows의
ffmpeg(영상을 녹화·변환하는 명령줄 프로그램)가 카메라 영상을 압축해 TCP로 보내고, WSL 안의 이 명령이 받아서 프레임마다
MediaPipe와 `DriverPipeline`을 돌린다. 명령줄 전부, 옵션, 터미널과 페이지에 나오는 것, 끝나는 길은 README 4.13절
"실시간 시험: Windows의 웹캠 (`python -m drowsy.live`)"에 있다. 순서만 적으면 이렇다.

1. (Windows, 한 번만) PowerShell에서 ffmpeg를 설치한다(`winget`. 명령은 README 4.13절). 그 명령은 실행해 보지 않았다.
2. (Windows PowerShell) 카메라 이름을 본다: `ffmpeg -hide_banner -list_devices true -f dshow -i dummy`.
3. (WSL 터미널) `python -m drowsy.live`. 보내는 쪽을 120초까지 기다린다. 보내는 쪽을 먼저 켜면 접속이 거부된다.
4. (Windows PowerShell, 3이 기다리는 동안) 3이 화면에 찍어 주는 `sender example`의 ffmpeg 명령에서 `<camera name>`을 2의
   이름으로 바꿔 실행한다. 3에 `source opened`와 `first frame`이 나오면 이어진 것이다. 접속이 거부되거나, 보내는 쪽이 돌기
   시작했는데도 `still waiting` 줄만 이어지면 명령 끝의 주소를 `tcp://127.0.0.1:5599`로 바꿔 본다(`python -m drowsy.live --help`
   끝의 안내 2번과 README 4.13절). Windows에서 이 PC로 연 TCP 접속은 두 이름 모두로 닿았지만, Windows의 ffmpeg로 영상을 보내 본
   적은 없다. 120초 안에 영상이 오지 않으면 3은 "아무도 접속하지 않았거나, 접속한 쪽이 MPEG-TS 영상을 보내지 않았다"는 오류(명령의
   `-f mpegts`를 보라는 안내가 붙는다)와 종료 코드 2로 끝나므로 3부터 다시 한다.
5. (Windows 브라우저) `http://localhost:8765/`를 연다. 상태와 카메라 미리보기가 나온다. 미리보기를 보며 얼굴을 맞춘다.
6. 처음 60초는 앞을 본다(기준선). 그 뒤에 (가)의 표에 있는 동작을 하면 이벤트가 터미널에 한 줄씩, 페이지의 최근 목록에 나온다.
7. WSL 터미널에서 Ctrl+C로 끝낸다. `wrote` 줄이 나올 때까지 기다린다. 그 앞의 `frames:` 줄이 받은 프레임이 어떻게 쓰였는지
   센다(풀어낸 수 = 타임스탬프로 버린 수 + 처리가 밀려 버린 수 + 끝에 남은 수 + 처리 오류가 난 수 + 처리한 수). `out/live/`에
   프레임 표(`.parquet`), 타임라인 그림, 이벤트 JSON이 생긴다. 표는 `python -m drowsy.demo --raw out/live/<파일 이름>.parquet`로
   다시 돌릴 수 있다. 보내는 쪽을 기다리는 동안 터미널 창을 닫거나 kill로 끝내면 빈 출력 폴더가 남는다.

알아 둘 것. 이 도구는 데스크톱 시험용이고 Android에 관해서는 아무것도 확인하지 않는다(기기의 `LIVE_STREAM` 모드, 프레임률,
지연과 무관하다). 그림은 H.264로 압축된 것이라 앱이 받는 카메라 프레임과 화소가 다르다. **이 도구를 만든 사람들은 실제
카메라, Windows의 ffmpeg, 브라우저에 그려진 페이지, 실제 얼굴로 돌려 보지 못했다.** 이 PC 안에서 얼굴 없는 합성 그림을
보내 본 실행에서는 보내는 쪽이 프레임을 압축기에 넣은 때부터 그 프레임의 처리가 끝날 때까지 중앙값 71.8 ms였다(README
4.13절의 "잰 것"). 판정의 시간은 프레임 시각에서 나오므로 이 지연은 이벤트에 들어가지 않는다.

## 6. Android에 잇기

이 장의 Kotlin 조각은 모두 **기기에서 실행해 보지 않은 예시**다. 정확한 동작은 `docs/SPEC.md`가 정한다. 저장소에는 Android
코드가 없고, 이 조각들은 컴파일해 보지 않았다.
가정: 조각에 나오는 `RawFrame`, `DriverPipeline`, `StepFeatures` 같은 이름은 Python 이름을 그대로 옮긴 것이다. 실제 이름과
패키지는 앱 팀이 정한다. 파일은 앱의 assets에 원래 이름으로 넣었다고 보았다.

### 6.1 번들할 파일

| 파일 | 어디서 받나 | 주의 |
|------|-------------|------|
| `drowsiness_v0.onnx` | `export/` | 무작위 가중치. 연동 확인용 |
| `feature_spec_v0.json` | `export/` | 모델과 짝이다. 이식 코드의 상수(`pipeline` 블록)를 여기서 읽는다 |
| `rules.json` | `export/` | 규칙과 경고의 임계값을 여기서 읽는다 |
| `face_landmarker.task` | 저장소에 없다. MediaPipe의 공개 표준 파일(float16, 버전 1)이다 | 받는 곳과 기대하는 sha256은 README 3장 "환경 준비"의 "face_landmarker.task" |

- `export/`의 세 파일은 **바이트 그대로** 넣는다. 손으로 고치거나 JSON을 다시 쓰거나 줄바꿈을 바꾸면 해시가 달라진다.
  앱 저장소에서도 이 파일들의 줄바꿈이 바뀌지 않게 한다. 이 저장소는 `.gitattributes`에 `export/*.json -text`,
  `*.onnx binary`, `*.task binary`를 두어 막았지만, 파일을 다른 저장소로 옮기면 그 설정은 따라가지 않는다.
- 상수는 Kotlin 코드에 적지 않고 두 JSON에서 읽는다. 실제 데이터를 본 뒤 잠정 상수가 한 번 바뀔 예정이기 때문이다(7.4절).
- 테스트 벡터(`tests/vectors/*.json`)는 앱에 넣는 파일이 아니라 이식 코드의 단위 테스트가 읽는 파일이다.

### 6.2 시작할 때의 검사

앱은 시작할 때 한 번 다섯 가지를 비교하고, 하나라도 다르면 판정을 시작하지 않는다(SPEC 15장 "앱이 해야 하는 해시 검사").
sha256은 파일 내용의 지문이다. 파일이 한 바이트라도 다르면 값이 달라진다.

| # | 비교 | 다르다는 것의 뜻 |
|---|------|------------------|
| H1 | `face_landmarker.task`의 sha256 = 모델 메타데이터 `mediapipe_model_sha256` = spec 파일의 `pipeline.mediapipe.model_sha256` | 학습과 다른 MediaPipe 모델이다 |
| H2 | `feature_spec_v{N}.json` 바이트의 sha256 = 메타데이터 `feature_spec_hash` | 모델과 짝이 아닌 spec 파일이다 |
| H3 | spec 파일 안의 `pipeline_hash` = 메타데이터 `pipeline_hash` = 이식 코드를 벡터로 맞출 때의 `pipeline_hash` | 검증한 것과 다른 상수다 |
| H4 | `rules.json` 바이트의 sha256 = 벡터의 `rules_hash`(빌드에 넣어 둔 값) | 검증한 것과 다른 규칙 설정이다 |
| H5 | 메타데이터 `step_sec` = `1`, `window_steps` = `120`, `class_order` = `alert,low_vigilant,drowsy`, `standardization` = `in_graph` | 계약이 다른 모델이다 |

다섯 가지가 모두 적힌 곳은 SPEC 15장이다. README 13.2절 "순서"도 2026-11-15부터 다섯 가지를 모두 적는다(전에는 셋만
적었다). `export/README.md`의 "어느 해시가 어느 파일과 짝인가"는 표 아래 문단(앱이 시작할 때 할 검사)에 둘(H2,
H3의 메타데이터 비교)을 적고, 같은 절의 표에서 `mediapipe_model_sha256`이 앱이 번들한 파일과 같아야 한다고 적는다(H1).
H4와 H5까지 하는 SPEC을 따른다.

`pipeline_hash`는 Python이 계산해 파일에 적어 둔 문자열이다. Kotlin은 계산하지 않고 문자열만 비교한다. 지금 값은
`feature_spec_hash` `f4031d09…`, `pipeline_hash` `650495e5…`, `rules_hash` `9c2d05f2…`, `mediapipe_model_sha256` `64184e22…`이고
전체 문자열은 `export/README.md`의 "어느 해시가 어느 파일과 짝인가"에 있다.

```kotlin
// 예시: 기기에서 실행해 보지 않았다. 정확한 동작은 docs/SPEC.md 14.3절과 15장이 정한다.
fun sha256Hex(bytes: ByteArray): String =
    MessageDigest.getInstance("SHA-256").digest(bytes).joinToString("") { "%02x".format(it) }
fun asset(name: String): ByteArray = context.assets.open(name).use { it.readBytes() }

val env = OrtEnvironment.getEnvironment()
val options = OrtSession.SessionOptions().apply {
    setIntraOpNumThreads(1)          // 참조 구현과 벡터가 쓰는 설정 (SPEC 14.1절)
    setInterOpNumThreads(1)
}
val session = env.createSession(asset("drowsiness_v0.onnx"), options)
val meta: Map<String, String> = session.metadata.customMetadata      // 값은 모두 문자열
val specBytes = asset("feature_spec_v0.json")
val spec = parseFeatureSpec(specBytes)        // 앱이 쓰는 JSON 파서로 읽는다. 바이트는 해시용으로 그대로 둔다
val rulesBytes = asset("rules.json")
val rules = parseRules(rulesBytes)            // 해시한 바이트와 같은 바이트에서 읽는다. 6.6절의 DriverPipeline에 넘긴다

val problems = buildList {
    if (sha256Hex(asset("face_landmarker.task")) != meta["mediapipe_model_sha256"]) add("H1 task")
    if (spec.pipeline.mediapipe.modelSha256 != meta["mediapipe_model_sha256"]) add("H1 spec")
    if (sha256Hex(specBytes) != meta["feature_spec_hash"]) add("H2")
    if (spec.pipelineHash != meta["pipeline_hash"] || spec.pipelineHash != VERIFIED_PIPELINE_HASH) add("H3")
    if (sha256Hex(rulesBytes) != VERIFIED_RULES_HASH) add("H4")
    if (meta["step_sec"] != "1" || meta["window_steps"] != "120" ||
        meta["class_order"] != "alert,low_vigilant,drowsy" || meta["standardization"] != "in_graph") add("H5")
}
```

`problems`가 비어 있지 않으면 판정을 시작하지 않는다. `VERIFIED_PIPELINE_HASH`와 `VERIFIED_RULES_HASH`는 이식 코드를 맞춘 벡터
파일에 적힌 두 값을 빌드에 상수로 넣은 것이고, `parseFeatureSpec`과 `parseRules`는 앱이 만드는 JSON 읽기 함수다(읽을 때의
검사는 6.5절). 대상 `onnxruntime-android` 버전이 opset 17과 IR 8을 읽는지는 앱 팀이 확인한다(SPEC 14.4절 "허용 연산자").
저장소가 확인한 것은 Python 쪽뿐이다. 이 저장소의 고정 버전은 onnxruntime 1.31.1이고(README 3장 "환경 준비"), 계획 단계의
조사에서 opset 17, IR 8 파일이 Python onnxruntime 1.15.1~1.31.1에서 모두 열렸다(PLAN 1.3절 "앱 팀에 전달할 확인 요청 (구현을
막지는 않음)").

### 6.3 MediaPipe 설정

SPEC 1장의 표(G1~G12)가 전부다. 학습 특징이 이 전제로 뽑히므로 하나라도 어긋나면 모델에 들어가는 값의 분포가 달라진다.
대부분은 오류 없이 값만 달라지므로 눈에 띄지 않는다.

| 지킬 것 | 까닭 |
|---------|------|
| 실행 모드는 `LIVE_STREAM`(`detectAsync`). `IMAGE` 모드는 쓰지 않는다 | 추적과 평활이 달라진다 |
| `numFaces = 1` | 1이 아니면 MediaPipe의 시간 평활이 꺼진다 |
| 블렌드셰이프 출력과 변환 행렬 출력을 **켠다** | 꺼져 있으면 `RawFrame`을 만들 수 없다 |
| 검출·추적 신뢰도 임계값은 기본값 그대로 | 얼굴 유무 판정이 달라진다 |
| 비트맵을 **똑바로 세워서** 넘긴다. `ImageProcessingOptions`의 `rotationDegrees`를 쓰지 않는다 | 그 옵션은 블렌드셰이프 값을 바꾼다 |
| 분석 프레임을 **좌우 반전하지 않는다**. 반전은 미리보기에만 건다 | 좌우 신호가 바뀌고 yaw·roll의 부호가 뒤집힌다 |
| 타임스탬프는 양수이고 엄격히 증가하는 **실제 ms**. 프레임 번호를 넘기지 않는다 | 0 이하는 MediaPipe의 평활을 흐트러뜨리고, 같거나 작은 값은 MediaPipe가 거부한다. 프레임 번호는 평활과 모든 시간 계산을 틀리게 한다 |

`LIVE_STREAM`은 MediaPipe의 세 실행 모드(`IMAGE`, `VIDEO`, `LIVE_STREAM`) 가운데 카메라용 비동기 모드다. 학습 특징은 Python
`mediapipe` 0.10.32의 `VIDEO` 모드로 뽑는다(README 3장 "환경 준비", SPEC 1장의 G2). 두 모드가 같은 그래프를 쓰고 같은
결과를 낸다는 것은 계획 단계의 조사에서 데스크톱 CPU로만 확인했다(PLAN 2.3절 "VIDEO 모드와 LIVE_STREAM의 일치, 타임스탬프
(검증됨, Android 실기기는 미실행)"). 앱이 쓸 MediaPipe 라이브러리(`tasks-vision`)의 버전은 저장소에 기록돼 있지 않다. 버전
사이의 수치 차이를 잰 기록은 PLAN 1.1절 "답이 필요한 것"의 Q1에 있다.

계획서의 조사 기록에 따르면 MediaPipe의 공식 Android 예제는 전면 카메라 프레임을 반전해서 넘긴다(PLAN 1.1절 "답이 필요한
것"의 Q3: 앱이 MediaPipe에 넘기는 프레임의 전제를 묻는 질문). 예제를 그대로 가져오면 위 전제가 깨지므로 그 부분을 확인한다.

```kotlin
// 예시: 기기에서 실행해 보지 않았다. 정확한 전제는 docs/SPEC.md 1장이 정한다.
val landmarker = FaceLandmarker.createFromOptions(
    context,
    FaceLandmarker.FaceLandmarkerOptions.builder()
        .setBaseOptions(BaseOptions.builder().setModelAssetPath("face_landmarker.task").build())
        .setRunningMode(RunningMode.LIVE_STREAM)
        .setNumFaces(1)
        .setOutputFaceBlendshapes(true)
        .setOutputFacialTransformationMatrixes(true)
        .setResultListener { result, input -> onResult(result, input) }
        .setErrorListener { e -> log(e) }
        .build()                                  // 신뢰도 임계값은 건드리지 않는다
)

// 카메라 프레임마다: uprightBitmap은 똑바로 세운, 좌우 반전하지 않은 비트맵이다
landmarker.detectAsync(BitmapImageBuilder(uprightBitmap).build(), frameTimeMs)
```

CPU와 GPU 가운데 어느 실행 장치(delegate)를 쓸지는 앱 팀이 정한다. 저장소는 GPU와 CPU의 수치 차이를 재지 못했다(SPEC 18장).
카메라는 운전자 정면에서 좌우 15도 이내에 두기를 권한다.

분석 영상의 해상도도 앱 팀이 정한다. 정할 때 알아 둘 것이 둘 있다. 첫째, 눈 하나의 가로 폭(그 눈의 양쪽 꼬리 사이의 픽셀
거리)이 6 px(`signals.min_eye_width_px`) 미만이면 그 눈은 "쓸 수 없는 눈"이 되고, 두 눈이 다 그러면 closure가 무효다
(SPEC 5.2절 "EAR과 홍채 비율", SPEC 3.4절의 `closure_valid`). 둘째, 얼굴이 프레임에서 너무 작으면 검출되지 않는다. 계획 단계의 조사에서는 얼굴 폭이
프레임 긴 변의 약 9% 아래로 내려가면 검출되지 않았다(PLAN 1.3절, `docs/MODEL_CARD.md` 7장 "상위 모델(MediaPipe)의 제한".
정면 사진 한두 장과 그 합성 변형으로 본 값이고 기기에서 잰 값이 아니다).

### 6.4 결과를 `RawFrame`으로 바꾸기

```kotlin
// 예시: 기기에서 실행해 보지 않았다. 정확한 동작은 docs/SPEC.md 1장과 3.1절이 정한다.
fun toRawFrame(result: FaceLandmarkerResult, input: MPImage): RawFrame {
    val t = result.timestampMs()                         // detectAsync에 넘긴 값
    val faces = result.faceLandmarks()
    if (faces.isEmpty())                                 // 얼굴 유무는 이것으로만 판정한다
        return RawFrame(t, false, input.width, input.height, emptyMap(), emptyMap(), DoubleArray(0))

    val lm = HashMap<Int, Pair<Double, Double>>()
    for (i in spec.pipeline.landmarks.requiredIndices()) {        // SPEC 4.1절의 44개
        val p = faces[0][i]
        lm[i] = Pair(p.x().toDouble(), p.y().toDouble())          // 정규화 좌표 그대로. 픽셀로 바꾸지 않는다
    }
    val bs = HashMap<String, Double>()
    for (c in result.faceBlendshapes().get()[0])                  // 이름으로 찾는다 (SPEC 4.2절)
        bs[c.categoryName()] = c.score().toDouble()
    val m16 = result.facialTransformationMatrixes().get()[0]      // float[16]. 순서를 바꾸지 않는다(열 우선)
    return RawFrame(t, true, input.width, input.height, lm, bs, DoubleArray(16) { m16[it].toDouble() })
}
```

- **얼굴이 없는 결과도 반드시 넣는다**(`face = false`). 빼면 그 시간이 "데이터 없음"으로 바뀌어 끊김 판정이 달라진다.
- `w`, `h`는 MediaPipe에 넘긴 영상의 크기다. EAR을 픽셀 좌표로 계산하는 데 쓰인다.
- 얼굴이 있는데 블렌드셰이프나 행렬이 없으면 참조 구현은 예외를 낸다. 6.3절의 두 출력을 켰는지부터 본다.

### 6.5 일곱 모듈을 옮기고 벡터로 맞추기

순서는 5.5절의 표다. 옮길 때 지킬 것은 SPEC 2장 "숫자 규칙"에 모여 있고, 틀리기 쉬운 것만 추리면 아래와 같다.

- 실수는 모두 `Double`, 시간은 정수 ms의 `Long`이다. `Float`는 모델 입력과 출력에만 나온다.
- 수학 함수는 `sqrt`, `atan2`, `hypot`, `sin`, `cos`, `floor`, `ceil`만 쓴다. 각도 변환은 상수를 곱한다. 참조 구현이 `floor`와
  `ceil`도 쓴다(`drowsy/calibrate.py`의 분위수 순위, `drowsy/blink.py`의 반올림). README 13.2절의 목록도 2026-11-15에 SPEC 2장에
  맞췄다(전에는 두 함수가 빠져 있었다).
- 반올림은 `floor(x + 0.5)`다. `kotlin.math.round`(짝수 쪽 반올림)를 쓰지 않는다.
- 비교 연산자를 명세에 적힌 그대로 옮긴다. `>=`와 `>`, `<`와 `<=`를 바꾸지 않는다.
- NaN과 무한대를 만들지 않는다. 없는 값은 0.0과 옆의 `Boolean`으로 나타낸다.
- 합은 명세에 적힌 순서로 더한다. 더한 값을 들고 다니며 빼는 식으로 바꾸지 않는다.
- 설정을 읽을 때 참조 구현과 같은 검사를 한다: 두 감김 검출기의 `0 < max_dt_ms <= hold_ms < clock.reset_gap_ms`, 하품과
  끄덕임의 `cancel_gap_ms < clock.reset_gap_ms`, `rules.json`의 `clock`이 spec 파일의 `clock`과 같은지(SPEC 10.1절 "호출 계약",
  11.5절 "하품과 끄덕임", 7.1절 "생성"). 세 검사는 SPEC과 코드(`drowsy/spec.py`의 설정 검증, `drowsy/pipeline.py`의 생성자)에
  있으므로 함께 옮긴다. README 13.2절도 2026-11-15부터 셋을 모두 적는다(전에는 두 감김 검출기의 검사만 적었다).

벡터 하나는 JSON 파일 하나다. 입력(`frames`, `speed`, `baseline`, `config_overrides`, `model`)과 참조 구현의 출력(`expected`),
항목별 허용 오차(`tolerances`)가 함께 들어 있다. 쓰는 법은 다음과 같다(`tests/vectors/README.md`의 "파일 형식", "허용 오차
(PLAN 10.2절)", "Android 팀이 쓰는 법").

1. 파일의 `pipeline_hash`와 `rules_hash`가 번들한 파일의 값과 같은지 본다. 다르면 상수가 다른 것이므로 비교를 멈춘다.
   모델을 쓰는 벡터(`model` 묶음과 `e2e`)는 번들한 모델 파일의 sha256이 벡터의 `model.sha256`과 같은지도 먼저 본다(v0은
   `eb2f71a6…`. 전체 문자열은 `export/README.md`의 "어느 해시가 어느 파일과 짝인가". 시작 검사 H1~H5에는 없는 비교다).
2. `frames`를 `RawFrame`으로 바꾼다. `lm`의 키는 문자열이므로 정수로 바꾸고, 숫자는 `Double`, `t_ms`는 `Long`으로 읽는다.
3. 묶음에 맞게 돌린다.
   - `signals` 묶음은 프레임마다 `signals.compute`만 부른다.
   - `model` 묶음에는 프레임이 없다. `model_inputs[i]`(원시 값 `[120][17]`. `[0]`이 가장 오래된 스텝)를 `float32 [1, 120, 17]`로
     바꿔 ONNX에 바로 넣고 `expected.probs[i]`의 `probs`와 비교한다(원소는 `{input: i, probs: [확률 3개]}` 모양이다).
   - 그 밖의 묶음(`baseline`, `runs`, `steps`, `rules`, `e2e`)은 `DriverPipeline(spec, rules, baseline, model)`을 만들어 프레임을
     차례로 넣는다. 여기서 첫 인자 `spec`은 spec 파일의 `pipeline` 블록이다(6.6절 조각의 `spec.pipeline`). `rules`에는 `config_overrides`를 덮어쓴다. 벡터의 `baseline`이 `null`이면 기준선 인자를 주지
     않고(파이프라인이 스스로 보정한다), 아니면 그 값을 넣는다. 벡터의 `model`은 셋 가운데 하나다. `null`이면 모델
     없이(`model = null`) 만든다. `kind`가 `stub`이면 i번째 호출(0부터)에 `probs[i]`를 돌려주고 목록이 끝나면 마지막 값을
     되풀이하는 가짜 모델을 넣는다(호출 수가 `probs`의 길이보다 많은 벡터가 있다). `kind`가 `onnx`이면 실제 ONNX를 넣는다.
   - `baseline`과 `runs` 묶음은 `DriverPipeline` 없이도 확인할 수 있다. `pipeline`을 옮기기 전에 맞춰 볼 때 쓴다(방법은
     `tests/vectors/README.md`의 "묶음과 벡터").
4. 출력을 모아 `expected`에 있는 항목만 비교한다. 실수는 `|실제 − 기대| ≤ abs + rel·|기대|`, 시각은 ±1 ms, 나머지(불리언,
   문자열, 스텝 번호, 목록의 길이와 순서, 세는 값)는 정확히 같아야 한다.

알아 둘 것 둘. 첫째, 벡터의 입력은 모두 합성 값이고 기대값은 참조 구현의 출력이다. 벡터를 통과한다는 것은 "Python과 같게
계산한다"는 뜻이지 성능이 좋다는 뜻이 아니다. 둘째, **벡터가 모두 통과해도 확인되지 않는 동작이 있다.** 표시용 상태
`gaze_zone`, 실수 임계값에 정확히 놓인 비교 등이다. 그 목록은 SPEC 16.1절 끝에 있고(지금 정리 중이다) 그 자리는 SPEC의 의사
코드와 연산자를 그대로 옮긴다.

### 6.6 프레임마다 파이프라인 부르기

```kotlin
// 예시: 기기에서 실행해 보지 않았다. 정확한 동작은 docs/SPEC.md 7장이 정한다.
val pipelineThread = Executors.newSingleThreadExecutor()          // update는 한 번에 하나씩, 순서대로
val pipeline = DriverPipeline(spec.pipeline, rules, model = ::runModel)    // 운전 한 번에 인스턴스 하나

fun onResult(result: FaceLandmarkerResult, input: MPImage) {      // MediaPipe의 결과 콜백
    val frame = toRawFrame(result, input)
    pipelineThread.execute {
        val out = pipeline.update(frame, latestSpeedKmhOrNull()) ?: return@execute   // null = 버린 프레임
        if (out.events.isNotEmpty()) showState(out.events)        // 상태 표시와 기록
        out.alerts.firstOrNull()?.let { warnDriver(it) }          // 첫 원소가 대표 경고다
    }
}
```

- 앱은 `baseline` 인자를 주지 않는다. 기준선은 파이프라인이 세션 앞부분에서 스스로 잡는다. 기준선을 넣는 길은 학습과 벡터용이다.
- `update`가 `null`을 돌려주면 타임스탬프가 같거나 거꾸로 온 프레임을 버린 것이다. 오류가 아니고 `dropped_frames`로 센다.
  다만 그런 타임스탬프는 MediaPipe가 먼저 거부하므로(SPEC 1장의 G8) `detectAsync`에 넘기기 전에 앱이 엄격히 증가하게
  만든다. 파이프라인의 버림은 그 뒤의 안전장치다.
- 파이프라인에는 "다시 시작" 메서드가 없다. 운전을 새로 시작하면 `DriverPipeline`을 새로 만든다.

### 6.7 스텝이 나왔을 때 ONNX 모델 부르기

모델을 부르는 시점은 앱이 정하지 않는다. 파이프라인이 창이 찼을 때 `model` 함수를 부른다(SPEC 7.2절의 6단계). 앱은 "120 x 17
값을 받아 확률 3개를 돌려주는 함수"만 넘겨주면 된다. 유한성 검사는 파이프라인이 부르기 전에 한다.

```kotlin
// 예시: 기기에서 실행해 보지 않았다. 정확한 동작은 docs/SPEC.md 14.1절이 정한다.
// window: 스텝 120개. window[0]이 가장 오래된 스텝이고, 원소는 StepFeatures.values(Double 17개, 특징 #0..#16)다.
fun runModel(window: List<DoubleArray>): DoubleArray {
    val buf = FloatBuffer.allocate(120 * 17)
    for (step in window)                       // 오래된 스텝부터
        for (v in step) buf.put(v.toFloat())   // 원시 값을 Float로 바꾸기만 한다. 표준화도 log1p도 하지 않는다
    buf.rewind()
    OnnxTensor.createTensor(env, buf, longArrayOf(1, 120, 17)).use { input ->
        session.run(mapOf("features" to input)).use { result ->
            val p = (result[0].value as Array<FloatArray>)[0]       // [1][3] = (alert, low_vigilant, drowsy)
            return doubleArrayOf(p[0].toDouble(), p[1].toDouble(), p[2].toDouble())
        }
    }
}
```

- 순서가 계약의 핵심이다. 스텝은 오래된 것부터, 스텝 안에서는 특징 #0부터 #16까지다. 거꾸로 넣어도 오류는 나지 않는다.
- 맞게 이었는지는 `model` 묶음(창 셋의 기대 확률)과 `e2e_250s`(프레임부터 확률까지 전 과정)로 확인한다. 허용 오차는 절대 1e-4다.
- 끊겼다가 온 프레임 하나가 이 함수를 최대 10번 부를 수 있다. 기기에서의 추론 시간은 잰 적이 없으므로 앱 팀이 잰다.
- `source: perclos`인 지금은 `model`을 넘기지 않아도(`null`) 이벤트와 경고가 같다. 그래도 연동을 확인하려면 넘긴다.

### 6.8 차량 속도 넘기기

필요한 값은 하나다. **지금의 차량 속도, km/h, `Double`, 알 수 없으면 `null`.** `update`를 부를 때마다 그때의 최신 값을 준다.

- 이 저장소에는 차량 플랫폼(Pleos Connect)이나 차량 신호에 대한 코드와 문서가 없다. 속도를 어느 API에서 어떤 단위와 주기로
  받는지는 **플랫폼 문서에서 확인해야 한다.** 단위가 km/h가 아니면 앱에서 바꿔서 넘긴다.
- 값을 받지 못하는 동안 `null`을 넘기면 속도 억제가 꺼져 정차 중에도 경고가 나간다. 그때 어떻게 할지는 앱이 정한다.
- 테스트 벡터의 `speed`는 `[[t_ms, kmh], ...]` 모양이다. 프레임의 `t_ms`가 그 값 **이상**인 프레임부터 그 속도를 넣는다. 첫
  항목보다 이른 프레임과 목록이 빈 벡터에는 `null`을 넣는다(0.0이 아니다. 0.0을 넣으면 속도 억제가 걸려 경고가 달라진다).

### 6.9 이벤트와 경고를 받아서 할 일

- `alerts`가 비어 있지 않으면 운전자에게 알린다. 여러 개가 함께 오면 첫 원소가 가장 급한 것이다.
- `events`는 상태가 바뀌는 순간(`onset`, `end`)에만 온다. 앱은 종류별로 "지금 진행 중인지"를 스스로 기억해 화면에 쓴다.
  `sleep`의 `onset`이나 `end`를 받으면 `microsleep`도 함께 끝난 것으로 정리한다. `sleep`까지 간 감김에는 `microsleep`의
  `end`가 오지 않는다(4.2절, SPEC 12.5절 "감김: `microsleep`, `sleep`").
- `calibrating`의 `onset`부터 `end`까지는 "보정 중"이다. 이 동안에 나는 이벤트(감김, 분석 불가)에는 `provisional = true`가
  붙는다.
- `calibrating`의 `end`는 보정이 성공했다는 뜻이 아니다. 180초까지 기준선을 잡지 못해 전역 상수로 대체된 경우에도
  난다(SPEC 12.2절 "`calibrating`"). 결과는 참조 구현의 읽기 전용 속성 `DriverPipeline.baseline`(보정이 끝나기 전에는
  `null`)의 `status`로 읽는다. 값은 셋이다: `ok`, `off_axis`(기준 자세의 yaw가 15도를 넘는다. 표시일 뿐이고 계산은 `ok`와
  같다), `fallback_global`(시선 규칙이 세션 내내 꺼진다. SPEC 8.3절 "정리"). 다시 보정하는 길은 `DriverPipeline`을 새로
  만드는 것뿐이다(3.3절). `fallback_global`일 때 그렇게 할지, 운전자에게 알릴지는 저장소에 정해져 있지 않다. 앱의 설계다.
- `unable_to_analyze`는 얼굴이 충분히 보이지 않는다는 뜻이다(프레임이 끊긴 경우 포함). 이 동안에는 시선과 감김 규칙이 멈춰
  있으므로, 조용한 것이 안전하다는 뜻이 아니다.
- 심각도(0~3)를 어떤 소리·진동·문구로 나타낼지는 저장소에 정해져 있지 않다. 앱의 설계다. 다만 이식 코드 안에 따로 거르는
  로직을 더하지는 않는다(벡터와 달라진다).
- 화면에 "전방 주시 중인지"를 보여 주고 싶으면 `DriverPipeline.gaze_zone`(`in`, `out`, `unknown`)이 있다. 표시용이고 판정에는
  쓰이지 않으며 벡터에 없다(SPEC 12.10절 "표시용 상태").

### 6.10 스레드와 타임스탬프

- `detectAsync`는 바로 돌아오고 결과는 나중에 콜백으로 온다. MediaPipe가 바쁘면 프레임을 버리므로 모든 카메라 프레임이 결과로
  돌아오지는 않는다(PLAN 2.3절 "VIDEO 모드와 LIVE_STREAM의 일치, 타임스탬프 (검증됨, Android 실기기는 미실행)"). 빠진
  프레임은 간격에서 200 ms를 넘는 부분만 "데이터 없음"이 된다.
- 프레임률이 얼마나 나와야 하는지는 상수에서 나온다(SPEC 17.2절 "프레임 간격이 길어질 때 (상수에서 나오는 값)"). 얼굴
  프레임이 평균 초당 5개에 못 미치면 60초 안에 300개를 채우지 못해 기준선이 늦어지고, 400 ms를 넘는 간격이 이어지면 분석
  불가(`unable_to_analyze`)가 시작된다. 15 fps에서 달라지는 것은 SPEC 17.1절 "프레임률에 따라 달라지는 것"에 있다.
- `update`는 **타임스탬프 순서로, 한 번에 하나씩** 부른다. 파이프라인의 상태 머신은 동시 호출을 가정하지 않는다.
  가정: 6.6절의 조각은 결과 콜백이 타임스탬프 순서로 온다고 보고 스레드 하나짜리 실행기에 넘겼다. 순서가 어긋난 프레임이
  오면 파이프라인이 버린다.
- ONNX 추론은 `update` 안에서 같은 스레드로 돈다. 화면과 소리는 UI 스레드로 넘긴다.
- `RawFrame.t_ms`는 결과의 `timestampMs()`를 그대로 쓴다. 시각의 원점은 무엇이든 되지만(파이프라인은 시각의 차만 쓴다)
  0 이하의 값과 프레임 번호는 안 된다. 카메라 프레임 시각을 권한다.
- 앱이 카메라를 10초 넘게 멈췄다가 이어 가면 파이프라인이 끊김으로 보고 스스로 다시 시작한다. 기준선은 남는다(3.6절).

### 7.2 알려진 한계

전체 표는 SPEC 18장 "알려진 교란과 거치 위치"와 `docs/MODEL_CARD.md` 8장 "알려진 실패 양상"이다. 앱을 만들 때 알아야 하는 것만 추린다.

- **눈 감김 상수와 임계값이 잠정이다.** closure를 만드는 상수와 감김 임계값(0.5, 0.7, 0.8)은 실제 눈 감김으로 확인한 적이 없다.
  마이크로슬립·수면·PERCLOS 판정이 실제 눈에서 어떻게 동작할지는 실제 데이터를 본 뒤에야 안다(SPEC 19장 "잠정 상수").
- **아래를 보거나 고개를 숙이거나 하품하면 눈을 감은 것처럼 읽힐 수 있다.** 보정하는 장치는 없다.
- **미러와 계기판을 보는 것도 시선 이탈로 센다.** 250 ms의 확정 시간과 3초 기준이 있을 뿐이다. 전방 주시 영역의 각도, 눈동자
  보조 임계값, 확정 시간은 공개 근거가 없는 잠정값이다(3초와 "30초 가운데 10초"는 Euro NCAP 2026의 값이고 잠정이 아니다.
  `config/rules.yaml`의 주석). 시선 규칙은 실내 영상인 학습 데이터로는 검증할 수 없어 합성 벡터로만 확인했다.
- **눈꺼풀이 반쯤 뜬 채 머무는 운전자**에게는 짧은 깜빡임이 한 감김으로 이어져 마이크로슬립·수면 경고가 날 수 있다. 소유자가
  그대로 두기로 정했다(README 8장 "소유자 결정 (2026-11-13, 2026-11-14)"의 소유자 결정 5, SPEC 10.5절 "경계 사례"의 7번).
- **세션 시작 239초 동안은 모델 출력이 없다.** 규칙은 그 시간을 기다리지 않는다.
- **5.2초~10초 끊긴 뒤**에는 분석 불가가 시작되어 얼굴이 5초 다시 보일 때까지 시선·감김 규칙이 멈춘다(결정 대기 6번).
- **약 15 fps에서는** 깜빡임 속도와 진폭이 작게 읽히고 아주 짧은 깜빡임을 놓칠 수 있다(SPEC 17장. 17.3절의 수치는 합성 파형의
  모사이고 실제 눈을 잰 값이 아니다).
- 안경, 선글라스, 가는 눈, 야간은 확인하지 못했다.
- **운전자가 옆으로 옮겨 앉으면** 기준 자세 대비 yaw와 pitch가 달라져 시선 규칙이 반응할 수 있다(실제 데이터로 확인한
  것이 아니라 설계와 조사에서 예상되는 것이다. 조사 기록은 PLAN 2.2절). 보정하는 장치는 없다. 기준선은 `DriverPipeline` 하나에 한 번만 잡으므로 다시 잡는 길은 새로 만드는
  것뿐이다(3.3절, SPEC 18장, `docs/MODEL_CARD.md` 8장 "알려진 실패 양상").
- **학습에 쓸 데이터(UTA-RLDD)는 운전 영상이 아니다.** 실내에서 화면을 보며 찍었고, 라벨은 본인 보고이며 영상 전체에 하나가
  붙는다. 여기서 학습한 모델이 차량으로 옮겨지지 않을 수 있다(README 6장 "데이터에 대한 전제"의 2번과 3번,
  `docs/MODEL_CARD.md` 6장 "데이터와 그 한계").
- **UTA-RLDD에는 명시된 라이선스가 없다.** 쓸지는 팀이 판단하고, 공모전 규정이 학습 데이터의 라이선스를 요구하는지 확인이
  필요하다(README 6장의 4번, PLAN 1.3절).
- MediaPipe의 모델 카드는 그 모델을 사람의 생명에 관련된 결정에 쓰지 말라고 적는다(`docs/MODEL_CARD.md` 7장 "상위
  모델(MediaPipe)의 제한"이 옮겨 적은 문장이다).

| 13~16 | 학습과 평가 | 재학습 길이와 후보 점수의 규칙, 모델을 판정에 쓸지 가릴 때의 집계 방식, 다른 정규화 조건과 부가 실행의 다루기 |
| 17 | 영상 추출 | 회전을 자동으로 가르지 못한 영상을 어떻게 확인할지 |

### 7.4 앞으로 바뀔 때 다시 받아야 하는 것

근거는 README 13.4절 "바뀔 때 알려 줄 것"이다.

- **실제 데이터로 잠정 상수를 확정하면** `pipeline_hash`가 바뀐다(다른 문서의 표현으로 "spec v1". 아래 주). spec 파일의
  바이트가 바뀌므로 `feature_spec_hash`도 바뀐다. 그래서 spec 파일, `rules.json`, 벡터와 함께 **그 spec 파일로 다시 내보낸
  모델 파일도** 다시 받는다. 모델 메타데이터에 두 해시가 들어 있어서, 옛 모델을 새 spec 파일과 함께 번들하면 6.2절의 H2와
  H3에 걸려 판정이 시작되지 않는다(README 3장 "환경 준비"의 "face_landmarker.task" 항목이 같은 귀결을 적는다). 빌드에 넣어
  둔 두 해시도 바꾼다. README 13.4절의 목록도 2026-11-15부터 모델 파일을 적는다(전에는 빠져 있었다).
  가정: 바뀌는 것이 상수의 값뿐이고 Kotlin 코드가 상수를 모두 JSON에서 읽는다면 코드는 고칠 것이 없다.
- **학습한 모델이 나오면** `drowsiness_v1.onnx`, `feature_spec_v1.json`(TCN이면 INT8 파일도)이 추가되고, 모델을 쓰는
  벡터(`model` 묶음과 `e2e`)가 다시 만들어지므로 벡터도 다시 받는다. 입출력 계약은 그대로다.
- **7.3절의 2~12번에 답이 오면** 답에 따라 코드, 벡터, SPEC, `export/`가 함께 바뀐다. 해시가 그대로인 변경도 있으므로 벡터
  폴더를 통째로 다시 받는다.

주: "spec v1"은 상수 묶음의 판(spec 파일 안의 `spec_version`)이 0에서 1이 된다는 뜻이다. 파일 이름 `feature_spec_v{N}.json`의
N은 이것이 아니라 모델 버전(메타데이터 `model_version`)이다. 두 번호는 따로 움직인다.

## 8. 용어

| 용어 | 뜻 |
|------|----|
| 이식, 참조 구현 | 동작의 기준이 되는 Python 코드(참조 구현)를 Kotlin으로 옮기는 일. 옮길 모듈은 일곱 개다 |
| 테스트 벡터 | 입력과 기대 출력을 담은 JSON. 옮긴 코드가 참조 구현과 같게 계산하는지 본다 |
| spec, spec 파일 | `feature_spec` 파일(`config/feature_spec.json`, 앱에는 `export/feature_spec_v{N}.json`). 특징 17개의 정의, 표준화 상수, 이식 코드의 상수 전부(`pipeline` 블록)를 담는다. "spec v0"의 0은 이 파일 안의 `spec_version`이고 파일 이름의 N(모델 버전)과 다른 번호다 |
| 랜드마크, 블렌드셰이프 | MediaPipe가 내는 얼굴 위 점들의 좌표와 표정 계수(`eyeBlinkLeft`, `jawOpen` 등 이름으로 찾는다) |
| EAR | 눈 가로세로비. 눈꺼풀 사이 거리를 눈 폭으로 나눈 값 |
| 기준선 | 세션 앞부분에서 잡는 그 운전자의 뜬 눈과 정면 자세의 기준값 |
| closure | 기준선에 대어 본 눈 감김 정도. 0은 뜬 눈, 1은 감은 눈 |
| 감김 구간 | 깜빡임이나 눈 감김 한 번. `ClosureRun` |
| PERCLOS | 최근 60초 가운데 closure가 0.8 이상이던 시간의 비율 |
| 세션, 세션 시간 | 운전 한 번(`DriverPipeline` 인스턴스 하나)과 그 첫 프레임부터 흐른 시간(ms) |
| 스텝 | 1초짜리 시간 칸. 스텝마다 특징 17개가 나온다 |
| 조회 구간, `full_lookback` | 특징이 돌아보는 과거의 길이(60초 또는 10초)와, 60초 구간이 다 찬 스텝이라는 표시 |
| 창 | 모델에 한 번에 넣는 연속 120스텝 |
| 유지 규칙, 데이터 없음 | 한 프레임의 상태를 다음 프레임까지 최대 200 ms만 이어진 것으로 보는 규칙. 넘는 부분이 "데이터 없음"이다 |
| 히스테리시스 | 시작 문턱과 끝 문턱을 다르게 두는 판정 방법 |
| `onset`, `end` | 이벤트의 단계. 상태가 시작됐다, 끝났다 |
| 재경고 대기 | 같은 종류의 경고를 낸 뒤, 그 종류의 상태가 새로 시작돼도 바로 경고하지 않는 시간. 이어지는 상태를 주기적으로 다시 경고한다는 뜻이 아니다 |
| VATS | 최근 30초 가운데 시선 이탈 시간을 더해 10초 이상이면 내는 이벤트 |
| 마이크로슬립, 수면 | 한 번의 감김이 1초 이상, 3초 이상 이어진 것 |
| 판정원 | `drowsy` 이벤트를 누가 판정하는지(`drowsiness.source`): PERCLOS 규칙, 모델, 둘 다 |
| 잠정 상수 | 공개 근거가 없거나 실제 데이터로 확인하지 못한 값. 실제 데이터를 본 뒤 한 번 확정한다 |
| ONNX, opset, 메타데이터 | 신경망을 담는 파일 형식, 그 연산자 묶음의 판 번호, 파일 안에 적어 둔 이름-값 쌍(버전과 해시) |
| 표준화, 온도 | 특징마다 평균을 빼고 표준편차로 나누는 처리와, 소프트맥스 앞에서 점수를 나누는 상수. 둘 다 그래프 안에 있다 |
| TCN, GRU | 모델 후보 둘. 시간축 합성곱 신경망과 순환 신경망 |
| 교차검증, fold, macro-F1 | 데이터를 묶음(fold)으로 나눠 번갈아 시험에 쓰는 평가 방법과, 세 클래스의 F1을 똑같은 무게로 평균한 점수 |
| sha256, 해시 | 파일 내용의 지문. `pipeline_hash`는 이식 코드의 상수 묶음, `rules_hash`는 규칙 설정 파일, `feature_spec_hash`는 spec 파일의 해시다 |
| UTA-RLDD | 학습에 쓸 계획인 공개 졸음 영상 데이터셋. 아직 받지 않았다 |

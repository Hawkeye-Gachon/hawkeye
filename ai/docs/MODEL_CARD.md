# 모델 카드: 운전자 졸음 판정 모델 (`drowsiness_v{N}.onnx`)

작성일 2026-11-13, 고친 날 2026-11-15(4차 검증 뒤의 정비까지). 상태: **v0 (무작위 가중치, 학습 전)**.

이 문서의 D 번호(D1, D7, D11처럼 D 뒤에 숫자가 붙은 표기)는 계획서 `docs/PLAN.md` 1.2절의 표에서 2026-11-13에 승인된
결정의 번호다. 소유자가 같은 날 따로 정한 네 가지 동작과 2026-11-14에 정한 한 가지(README 8장의 "소유자 결정 1~5")와는 다른
번호다. 자주 나오는 것:
D1 정규화 조건 셋의 비교, D7 영상 정확도의 분모와 품질 기준, D8 2클래스 정확도를 3클래스 모델로 내는 방법, D9 오경보의 정의,
D10 최종 모델과 보고 수치의 관계, D11 모델을 기본 졸음 판정원으로 둘지 가리는 기준(9장), D13 얼굴 프레임을 저장하지 않음,
D15 범위 밖, D16 INT8 양자화. README 맨 앞의 표에 뜻이 모두 있다.

> **이 모델에 대해 측정된 성능 수치는 아직 없다.** 실제 데이터(UTA-RLDD)가 준비되지 않아 학습과 평가를 하지 못했다.
> 아래 10장의 지표 표는 모든 칸이 `미측정`이다. 합성 데이터로 돌려 본 점수는 파이프라인 점검용이므로 이 문서에 싣지 않는다.
> 이 모델은 보조 안내용이며 안전 시스템이 아니다.

## 2. 입력과 출력

모델에 들어가는 것은 영상이나 랜드마크가 아니라 스텝 특징이다. 앱은 MediaPipe FaceLandmarker의 출력에서
이식 코드(`drowsy/signals.py` ~ `drowsy/pipeline.py`를 옮긴 것)로 스텝 특징을 계산해 넣는다.

- **입력** `features`: float32 `[1, 120, 17]`. 표준화하지 않은 원시 스텝 특징. `features[0][0]`이 가장 오래된 스텝,
  `features[0][119]`가 가장 최근 스텝이다. 값은 모두 유한해야 한다(유한하지 않으면 추론을 건너뛴다).
- **출력** `probs`: float32 `[1, 3]`. 순서는 alert, low_vigilant, drowsy. 합은 1이다.
- **그래프 안의 처리**: `log1p(max(x, 0))`(특징 #9~#12, #14) → `(x − mean) / std` → ±5 자르기 → 신경망 → 온도로 나누기
  → 소프트맥스. 앱은 표준화를 하지 않는다(메타데이터 `standardization=in_graph`).
- **형식**: ONNX opset 17, IR 8, 단일 파일, 배치 1 고정.
- **계약 검사**(`verify_contract`, 내보낼 때마다 돈다): 위 형식과 메타데이터, 허용 연산자, 그래프 안 처리의 배선과 상수를
  spec 사본과 대조한다. 2차 검증 뒤의 정비에서 온도 규칙이 엄격해졌다: 신경망의 점수(logits)를 바꿀 수 있는 것은 Softmax
  바로 앞의 `temperature` 상수로 나누기뿐이고, 기본 경로와 INT8 파일은 온도가 1.0이어도 그 상수를 가져야 하며(대체 경로
  `--dynamo`의 파일만 온도 1.0일 때 없을 수 있다), logits가 Div나 Mul 노드의 출력이면 거부한다. 3차 검증 뒤의 정비에서는
  logits를 내는 노드도 고정했다: 기본·대체 경로는 그래프의 유일한 Gemm(`alpha = beta = 1`, 상수 가중치와 편향), INT8 파일은
  양자화한 그 층의 끝인 편향 Add여야 한다. 4차 검증 뒤의 정비에서는 그 Gemm의 속성(`alpha`, `beta`, `transA`)과 INT8 Cast의
  형(`to`)이 한 번만, 정해진 형으로, 값을 가진 채 있어야 하고, 아니면 Python 오류가 아니라 한 줄의 계약 오류로 거부한다.
  계약의 값은 바뀌지 않았고 v0은 그대로 통과한다. 이 검사가 보지 못하는 것: 마지막
  층의 가중치와 편향을 통째로 줄이거나 키운 파일, 신경망 안쪽의 변경. 가중치는 체크포인트와 출력을 견주는 일치 검증이 지킨다.
- **출력 시점**: 1초마다. 첫 출력은 세션 시작 239초 뒤다(기준선 60초 + 조회 구간 60초 + 120스텝). 기준선이 연장되면 그만큼
  늦어진다(최대 약 6분). 규칙(마이크로슬립, 수면, 시선 이탈)은 이 시간을 기다리지 않는다.
- **메타데이터**(값은 모두 문자열): `model_version`, `feature_spec_hash`, `step_sec`, `window_steps`, `class_order`,
  `trained_on`, `commit`, `standardization`, `pipeline_hash`, `mediapipe_model_sha256`. 해시와 파일의 짝은 `export/README.md`에 있다.

## 3. 구조 후보와 v0의 실측 크기

내보낼 후보는 둘이고, 어느 쪽을 쓸지는 교차검증 안에서 고른다(4장). 아래 수치는 **무작위 가중치**로 내보내며
`python -m drowsy.export_onnx`가 출력한 값이다(2026-11-13, 개발 PC, F = 17). 크기와 속도만 알려 주고 정확도와는 무관하다.

| | 인과 TCN | 단방향 GRU |
|---|---|---|
| 구성 | 잔차 블록 5개(블록당 인과 확장 합성곱 2개, 커널 3, 확장 1·2·4·8·16, 합성곱 뒤 배치 정규화, ReLU, 드롭아웃), 마지막 스텝 읽기, 선형 3. 수용 영역 125스텝 | GRU 1층, 마지막 은닉 상태, 드롭아웃, 선형 3 |
| 기본 크기 | 채널 32 | 은닉 64 |
| 파라미터 수 | 30,915 | 16,131 |
| ONNX 파일 크기 | 148,558 bytes | 68,343 bytes |
| 그래프의 연산자 | Add, Clip, Concat, Constant, Conv, Div, Gather, Gemm, Log, Mul, Relu, Softmax, Sub, Transpose | Add, Clip, Concat, Constant, Div, Expand, GRU, Gather, Gemm, Log, Mul, Relu, Shape, Softmax, Sub, Transpose, Unsqueeze |
| 계약 검사(`verify_contract`) | 통과 | 통과 |
| PyTorch 대 onnxruntime 최대 절대 오차(무작위 원시 입력 200개, 허용 1e-4) | 1.192e-07 | 5.960e-08 |
| onnxruntime CPU 지연(1,000회, 연산 내부 스레드 1개) | 중앙값 0.0637 ms, 95 분위수 0.0853 ms | 중앙값 0.0646 ms, 95 분위수 0.0878 ms |
| 명령 | `python -m drowsy.export_onnx --random-init --kind tcn --version 0 --out-dir <임시 폴더>` | `python -m drowsy.export_onnx --random-init --kind gru --version 0 --out-dir <임시 폴더>` |

- 저장소의 `export/drowsiness_v0.onnx`는 TCN 쪽이다(sha256 `eb2f71a6e6defea6ea3c27da7c02ca244caba769b1ee241674158db045723842`).
  위 표의 TCN 값은 같은 명령을 임시 폴더(`--out-dir`)에 다시 실행해 얻었고, 그 파일은 저장소의 것과 바이트 단위로 같았다.
  `--out-dir`을 빼면 `paths.export_dir`(`export/`)에 쓰므로 GRU 명령은 저장소의 v0을 덮어쓴다. 시험할 때는 늘 임시 폴더를 준다.
- 2026-11-13과 2026-11-14, 정비 뒤에 두 명령을 임시 폴더로 다시 돌렸다. 파라미터 수, 파일 크기, 연산자, 최대 절대 오차는
  표와 같았고 TCN 파일은 저장소의 것과 바이트 단위로 같았다(지연은 다른 작업과 겹쳐 재서 표의 값을 그대로 둔다).
- 지연은 이 PC에서 한 번 잰 값이다. 대상 기기(Android)에서는 재지 않았다.
- 두 후보 모두 목표(파라미터 10만 개, 파일 1 MB)보다 훨씬 작다.
- INT8 양자화 파일은 TCN이 최종 모델일 때만 만든다(D16). v0에는 없다. `train final`이 적는 INT8 수치는 float 모델과의
  최대 확률 차이일 뿐이고, 지표 변화는 교차검증의 fold 모델 INT8 비교(10장)에서 읽는다.

## 4. 학습 절차 (설계. 실제 데이터로는 아직 실행하지 않았다)

코드는 `drowsy/train.py`, `drowsy/dataset.py`, `drowsy/evaluate.py`, `drowsy/baseline_lgbm.py`에 있고 합성 데이터로 전 과정이
도는 것만 확인했다.

- **창**: 스텝 특징 120개(120초). 신경망의 학습 창은 영상의 보폭 1 창에서 고르게 뽑는다(PLAN 5.2절의 "학습 보폭 5초,
  시작 위치 무작위 이동"과 같은 분포). 평가 보폭 1초. 영상 라벨을 창이 물려받는다.
  조회 구간이 덜 찬 스텝과 기준선 수집 구간은 창에 넣지 않는다.
- **정규화 조건**: 내보낼 모델은 "alert 영상 기준선" 조건으로 학습한다(피험자의 alert 영상에서 잡은 기준선으로 세 영상을
  정규화). 비교 조건은 "전역 정규화"와 "각 영상 자신의 앞 60초 기준선"(앱의 실제 동작)이다(D1).
- **손실과 표집**: 라벨 스무딩 0.1의 교차 엔트로피. 표집은 피험자 → 영상 → 출처 → 창 순서로 균등하다. 출처의 몫은 원본
  추출 0.5, 약 15 fps 모사 추출 0.25, 프레임 누락 변형 0.25다(가정. 출처가 없으면 그 몫은 원본으로 간다). 학습 피험자의
  창만 쓰고 내부 검증, 시험, 온도 맞추기는 원본 창만 쓴다.
- **최적화**: AdamW, 학습률 1e-3, 가중치 감쇠 1e-2, 배치 64. 200 갱신을 한 단위로 최대 60단위, 내부 검증 macro-F1 기준
  조기 종료(인내 10단위).
- **탐색 범위(사전 고정)**: TCN 채널 {16, 32} × 드롭아웃 {0.1, 0.3}, GRU 은닉 {32, 64} × 드롭아웃 {0.1, 0.3}.
- **증강**: 표준화 공간의 가우시안 잡음(σ = 0.05), 기기 프레임 누락 모사(약 15 fps) 추출을 학습 표본에 섞기
  (`training.fps_sim_share`), 저장된 신호에서 세션마다 10~30%의 프레임을 무작위로 버리고 특징을 다시 계산한 변형을 섞기
  (`training.frame_drop_share`). 15 fps 모사 추출이 원본의 세션을 다 덮지 못하면 학습을 시작하지 않는다. 표준화 상수도
  출처의 몫으로 가중한다.
- **부가 실험(PLAN 11장 E3)**: 순서형 소프트 라벨(정답 클래스가 이웃 클래스에 0.2를 나눠 준다), 속도 특징 #7, #8을 0으로
  둔 학습, 15 fps 모사 추출에서의 평가, fold 모델의 INT8 비교. 결과는 리포트의 부가 절에만 실리고 D11에 쓰지 않는다.
- **표준화와 확률 보정**: 평균·표준편차는 학습 창에서만 계산해 그래프와 `feature_spec_v{N}.json` 양쪽에 넣는다.
  온도 하나를 내부 검증 예측으로 맞춰 그래프에 넣는다.
- **교차검증**: UTA-RLDD의 공식 5-fold(fold k = 피험자 12(k−1)+1 ~ 12k). 바깥 fold를 시험으로 두고 나머지 4개 fold 안에서
  계열·설정·학습 길이·온도를 고른 뒤, 48명 전체로 다시 학습해(시드 3개) 시험 fold를 한 번만 평가한다.
  시험 fold는 선택, 조기 종료, 표준화 상수, 온도 어디에도 쓰지 않는다. 피험자 분리는 `assert_subject_disjoint`가 검사한다.
  누설 회귀 시험(`tests/test_leakage.py`)은 시험 fold의 한 피험자 데이터를 망가뜨린 사본으로 교차검증 명령 여덟 개를 돌려,
  그 fold의 선택 기록과 같은 fold의 손대지 않은 피험자의 예측이 모든 예측 묶음(44개)에서 바뀌지 않는지 본다. 3차 검증 뒤에는
  그 피험자의 라벨 파일만 맞바꾼 사본도 돌려, 평가받는 피험자 자신의 시험 라벨이 그 피험자의 확률에 닿지 않는지 본다. 저장소
  사본에 일부러 넣은 누설 10가지 가운데 8가지(시험 fold로 표준화하기, 시험 fold로 온도 맞추기 포함)를 잡았고(잡지 못한 둘은
  출력이 바뀌지 않는 경우였다), 3차 검증 뒤에는 자기 라벨로 온도를 다시 맞추거나 확률에 정답 라벨을 섞는 누설 넷도 잡았다
  (작업자의 기록). 이것은 절차의 검사이고 성능 수치가 아니다. 이 시험이 잡지 못하는 누설도 있다(4차 검증 뒤에 시험의 설명에
  적었다): 평가받는 피험자의 alert 대 나머지 라벨만 쓰는 누설, 리포트를 쓰는 시점(`drowsy.evaluate`)의 누설, 그리고 이 시험이
  돌리지 않는 `baseline_lgbm probes`와 `train final`의 누설.
  예외는 closure 상수와 전역 상수다. 이것은 E0에서 라벨 없이, 시험 피험자의 영상을 포함한 전체 영상으로 한 번 정하며
  교차검증 리포트의 설명에 그 사실이 적힌다(PLAN 4.3절).
- **최종 모델**: 같은 선택 절차를 60명 전체에 한 번 적용한 뒤 60명으로 학습한다(시드 0). 따라서 **보고할 수치는 같은
  절차의 교차검증 추정치이고, 내보낸 파일 자체를 시험한 값이 아니다**(D10).
- **비교 기준선**: 같은 fold로 학습한 LightGBM(창마다 특징별 통계 6개, 입력 102개). 내보내지 않는다. 신경망과 달리 원본
  프레임률 추출의 창(학습 보폭 격자 위의 창)으로만 학습한다. 그래서 비교표와 D11의 기준 LightGBM은 신경망의 두 증강
  (15 fps 모사 추출, 프레임 누락 변형) 없이 학습한 것이고, 그 리포트의 첫 문단에 그렇게 적힌다.

## 5. 쓰임새

**의도한 쓰임**: 운전자 보조 앱이 운전자에게 주는 참고용 안내(예: 휴식 권유). 규칙 엔진의 이벤트와 함께, 사람이 최종
판단을 하는 상황에서 쓴다.

**쓰면 안 되는 곳**

- 안전 시스템. 차량 제어, 자동 개입, 운전자의 주의를 대신하는 용도에 쓰지 않는다. 모델이 조용하다고 해서 운전자가
  깨어 있다는 뜻이 아니다.
- 사람의 생명에 관련된 결정(7장의 상위 모델 제한 참조).
- 운전 적합성, 근무 평가, 보험, 법적 책임, 의료 진단의 근거.
- 사람을 식별하거나 감시 기록을 만드는 용도. 모델은 얼굴 이미지를 받지 않고 스텝 특징만 받는다.
- 학습 조건 밖의 환경에서 검증 없이 쓰는 것: 야간·적외선 카메라, 선글라스, 얼굴이 작게 잡히는 거치 위치, 전면 RGB
  카메라가 아닌 입력.

## 6. 데이터와 그 한계

학습에 쓸 계획인 데이터는 UTA-RLDD다. 아직 받지 않았고 저장소에도 없다. 아래는 계획 단계의 조사(PLAN 2.4절: 논문,
데이터셋 페이지, 공개 코드, 미러의 파일 목록 기준)에서 확인한 내용이고 영상 자체는 재 보지 않았다.

- 피험자 60명, 논리 영상 180개(피험자마다 세 상태), 영상당 약 10분.
- **라벨은 본인 보고다**: alert는 KSS 1~3, low vigilant는 6~7, drowsy는 8~9. 영상 전체에 라벨 하나가 붙는다. 창마다의
  실제 상태는 알 수 없다.
- **실내에서 화면을 보며 찍은 영상이고 운전 환경이 아니다.** 주행 중의 조명 변화, 진동, 시선 이동, 거치 각도가 없다.
  차량으로 옮겨지지 않을 수 있다.
- 프레임률은 30 fps 미만이고 대부분 가변 프레임률이다. 일부 영상은 회전 보정이 필요하다.
- **회전을 자동으로 가르지 못하는 영상이 있을 수 있다.** 추출은 영상마다 0·90·180·270도를 시험해 얼굴 검출률과 머리
  기울기(roll)로 각도를 고르지만, 랜드마커가 거꾸로 선 얼굴도 검출하면 정반대 두 각도(0도와 180도)를 가르지 못한다. 그런
  영상은 "가르지 못함"으로 표시되고 추출 리포트, 스텝 표 명령, E0, 라벨 없는 영상 평가가 알린다. 3차 검증 뒤에는 학습과
  LightGBM 명령도 학습 전에 같은 줄을 출력하고 실행 기록(`run.json`, `final.json`, `probes.json`의 `rotation_check`)과 리포트
  설명에 그 수를 남긴다. 그래도 학습에서 빼지는 않는다. 그래서 실제 데이터로는 추출 뒤 학습 전에 `python -m drowsy.dataset`으로
  목록을 먼저 본다(README 4.9절의 순서).
  사람이 보고 보정표에 각도를 적기 전에는 180도 틀린 신호가 학습과 평가에 들어갈 수 있다(공개 사진 두 장으로 만든 클립
  184개의 검증에서 틀린 클립은 모두 표시됐다. RLDD로는 재 보지 않았다). 표시된 영상을 어떻게 확인할지는 소유자의 결정을
  기다린다(README 9장 17번).
- 클래스마다 녹화 세션이 다르다. 모델이 졸음 대신 조명·카메라·프레임률을 배울 위험이 있다(세션 교란). 대응으로
  녹화 조건을 드러내는 특징을 뺐고, 교란 점검 두 가지와 "앱 조건 평가"를 리포트에 싣는다.
- **명시된 라이선스가 없다**(논문 인용 조건과 얼굴 공개 제한만 있다). 사용 여부는 팀이 판단한다. 영상과 얼굴은
  재배포하지 않는다.
- **얼굴을 공개해도 되는 피험자는 60명 중 36명뿐이다.** 이 저장소의 데모와 리포트는 신호와 타임라인만 그리고 얼굴
  프레임을 저장하지 않는다(D13).
- 60명은 적다. fold당 영상 36개라 영상 하나가 정확도 2.8%p다. alert 영상의 평가 가능 시간은 전체 약 6시간이어서
  오경보 수치의 근거가 얇다.
- **기준선 전제**: 정규화는 "주행(영상) 시작 시점의 운전자는 각성 상태이고 전방을 본다"는 전제에 선다. 처음 60초에
  이미 졸린 운전자에게는 기준이 틀어진다.

## 7. 상위 모델(MediaPipe)의 제한

스텝 특징은 MediaPipe FaceLandmarker(`face_landmarker.task`, float16 v1, sha256 `64184e22…bc9ff`)의 랜드마크와
블렌드셰이프에서 나온다. 상위 모델의 제한이 그대로 이 모델의 제한이다. 아래 인용은 계획 단계의 조사 기록에서
옮긴 것이다(FaceMesh V2 모델 카드 2022-09-15, Blendshape V2 모델 카드 2022-11-11. PLAN 12장).

- 두 모델 카드 모두 범위 밖 용도에 이렇게 적는다: "This model is not intended for human life-critical decisions."
- 두 카드 모두 "Optimized for videos captured on front-facing cameras of smartphones."라고 적고, 주된 용도를
  "AR entertainment"로 든다. 차량 안의 거치 각도, 진동, 야간, 선글라스는 문서화된 동작 범위 밖이다.
- 입력 제한으로 적힌 것: 카메라에서 고개를 돌린 얼굴("more than 80 degrees"), 일부만 보이는 얼굴("less than 50% of
  the face"), 카메라에서 너무 먼 얼굴. 조명 저하, 잡음, 움직임, 가림은 떨림을 키운다.
- 블렌드셰이프 모델의 입력은 FaceMesh 랜드마크 146개의 x, y뿐이다. 그래서 `eyeBlink`와 EAR은 독립된 두 측정이
  아니라 같은 랜드마크의 두 함수다.

이 프로젝트의 조사에서 따로 확인한 것(PLAN 2.1절, 정면 사진 한두 장과 합성 변형): `eyeBlink`는 뜬 눈에서 0.19~0.30이고
눈꺼풀이 기하적으로 완전히 닫혀도 0.37~0.82에 그친다. yaw 30도에서 먼 쪽 눈의 EAR이 33% 커지고 아래 방향 pitch
30도에서 22% 작아진다. 얼굴 폭이 프레임 긴 변의 약 9% 아래로 내려가면 검출되지 않았다. 안경, 가는 눈, 실제 아래
시선, 실제 눈 감김은 검증하지 못했다.

## 8. 알려진 실패 양상

실제 데이터로 확인한 것이 아니라 설계와 조사에서 예상되는 것이다.

| 상황 | 일어나는 일 |
|------|-------------|
| 아래를 보거나 고개를 숙임 | closure가 올라간다. 감김으로 읽혀 PERCLOS와 감김 특징이 커진다. pitch 보정은 넣지 않았다 |
| 하품 | 하품 중에도 EAR이 내려가 closure가 올라간다 |
| 고개를 옆으로 돌림 | 25도부터 먼 쪽 눈을 쓰지 않고, 40도를 넘으면 closure가 무효다. 그 시간은 감김 특징의 유효 시간에서 빠진다(얼굴 시간에는 들어가므로 `face_missing_ratio`는 늘지 않는다) |
| 처음 60초에 이미 졸림 | 기준선이 감긴 쪽으로 잡혀 이후의 감김이 작게 읽힌다 |
| 낮은 프레임률(약 15 fps) | 깜빡임 속도가 절반 가까이 낮게, 진폭도 작게 읽힌다. 약 70 ms보다 짧은 깜빡임은 놓칠 수 있다(가정한 파형의 모사 `python -m drowsy.signal_check blink-sim`: 15 fps에서 진입 임계값 위 60 ms인 깜빡임의 검출 34.0%, 80 ms부터 100%. 눈을 잰 값이 아니다) |
| 눈을 반쯤 뜬 채 머무름 | 규칙용 0.5~0.7(특징용 0.3~0.5)에 머무는 시간은 감김 길이에 들어가지 않지만(2026-11-13 소유자 결정), 구간은 이탈 임계값 아래로 내려가야 끝나므로 그 양쪽의 감김은 한 구간으로 이어져 길이가 쌓인다. 짧은 깜빡임이 모여 마이크로슬립·수면이 될 수 있다(합성 각본: 눈꺼풀 0.6에 머물고 4초마다 0.9로 165 ms 깜빡이면 24.1초에 마이크로슬립, 72.0초에 수면(정확한 30 fps 시각이면 68.1초), 그 뒤 수면 경고가 3초마다 되풀이). 소유자가 2026-11-14에 이 동작을 그대로 두기로 정했고("지금대로 둠", README 8장의 결정 5) 알려진 한계로 남는다. 규칙 엔진의 동작이라 모델의 출력과는 무관하다 |
| 앱이 프레임을 좌우 반전하거나 `rotationDegrees` 옵션으로 회전 | 모델 특징은 좌우 대칭이라 반전에는 영향받지 않게 설계했다. `rotationDegrees` 옵션은 블렌드셰이프를 최대 0.19~0.43 바꾼다. 비트맵을 세워서 넘겨야 한다 |
| 운전자가 옆으로 옮겨 앉음 | 기준 자세 대비 yaw가 변해 시선 규칙이 반응할 수 있다(모델이 아니라 규칙의 문제) |
| 안경, 선글라스, 가는 눈, 야간 | 검증하지 못했다 |
| 스텝 특징에 NaN이나 무한대 | onnxruntime의 GRU는 NaN 입력에도 그럴듯한 확률을 낸다. 그래서 추론 전에 유한성을 검사하고 건너뛴다 |
| low vigilant 구분 | 문헌에서 이 클래스의 재현율은 우연 수준에 가깝다. 같은 결과가 나올 수 있다 |
| 세션 시작 직후 | 첫 239초 동안은 출력이 없다 |
| 6초 넘게 눈을 감은 무반응 운전자, 휴대전화 사용, 미러·계기판 확인 | 구분하지 않는다(범위 밖, D15) |

closure를 만드는 상수(`RHO`, `B_CLOSED`)와 감김 임계값(0.5, 0.7, 0.8)은 **실제 눈 감김으로 검증되지 않은 잠정값**이다.
실제 데이터를 본 뒤 한 번 확정한다(PLAN 11장 E0). 그 전의 모든 결과는 이 상수에 묶여 있다.

## 9. D11 판정 기준과 "실험용"의 뜻

규칙 엔진의 `drowsy` 이벤트는 판정원을 설정으로 고른다(`drowsiness.source: model | perclos | either`).
모델을 기본 판정원으로 두는 것은 교차검증 결과(앱 조건 평가, 즉 alert 영상 기준선으로 학습한 fold 모델을 시험 fold의
자기 세션 기준선 특징으로 평가한 값)가 아래를 **모두** 만족할 때뿐이다(D11, `config/default.yaml`의 `evaluation.model_gate`).

| 조건 | 기준 |
|------|------|
| 창 단위 macro-F1 | LightGBM 기준선 − 0.02 이상 |
| 2클래스(alert 대 drowsy) 영상 정확도 | 70% 이상 |
| alert 영상의 오경보 | 시간당 2회 이하 |
| 판정이 한 번이라도 난 alert 영상 | 10% 이하 |
| 판정이 난 drowsy 영상 | 50% 이상 |

- 이 기준은 점추정 규칙이다(구간을 보지 않는다). 판정은 교차검증의 주 결과 행으로 하고 내보낸 파일로 하지 않는다.
- 지금 코드는 분류 두 조건(macro-F1, 2클래스 영상 정확도)에 fold 평균(시드 평균)을, 오경보 세 조건에 5개 fold를 합친
  값을 쓴다. 이 집계 방식은 소유자의 확인을 기다린다(README 9장 14번).
- **지금 상태: 판정하지 않았다**(실제 데이터가 없다). 그래서 `drowsiness.source`는 `perclos`이고 모델은 "실험용"이다.
- **"실험용"의 뜻**: ONNX 파일은 계약대로 내보내고 앱은 확률을 계산해 기록하거나 표시할 수 있다. 그러나 그 확률은
  `drowsy` 이벤트와 경고를 만들지 않는다. 졸음 판정은 PERCLOS 규칙(`perclos_60 ≥ 0.15`가 10스텝 연속)이 하고,
  마이크로슬립·수면·시선 이탈 규칙은 모델과 무관하게 동작한다. 기준을 통과하지 못한 모델도 같은 상태로 남는다.
- PERCLOS 규칙의 임계값도 잠정값이며, 같은 방식으로 평가해 모델과 나란히 싣는다.

## 10. 지표

모든 칸이 `미측정`이다. 실제 데이터로 교차검증을 돌린 뒤 채운다. 채울 때는 fold별 값(시드 평균), fold 평균 ± 표준편차,
시드 간 표준편차, 피험자 단위 부트스트랩 95% 구간을 함께 싣고, 생성 명령과 리포트 폴더를 적는다. 합성 데이터로 돌린
값은 어느 칸에도 넣지 않는다.

**생성 명령이 있는 행**(2026-11-14 기준, 실제 데이터 설정 `config/local.yaml`로 돌린다. README 4장). Android 기기 행을 뺀
모든 행에 생성 명령이 있다.

- 첫 표의 행 전부와 D11 판정: `python -m drowsy.baseline_lgbm --config config/local.yaml --run-name <이름> cv`
  다음 `python -m drowsy.train --config config/local.yaml --run-name <이름> cv`(같은 이름). LightGBM 열은 앞 명령, PERCLOS
  열은 뒤 명령의 오경보 표에서 온다. INT8 행은 뒤 명령의 부가 묶음(`tcn_onnx`, `tcn_onnx_int8`: fold마다 다시 학습한 TCN을
  내보내 양자화하고 onnxruntime으로 시험 fold에 돌린 것)과 그 짝지은 비교에서 온다.
- 정규화 조건 셋의 비교: 위 두 명령에 `--arms alert_baseline global session_baseline`(LightGBM), `--arm <조건>`(신경망).
  내보낼 조건(`training.export_arm`)이 아닌 신경망 실행은 지금 부가 결과로 표시된다(소유자 결정 대기, README 9장 15번). 그런 실행은 D11 판정을 하지 않고 그렇게 적힌 리포트를 쓴다.
- closure `W`의 비교: `python -m drowsy.baseline_lgbm --config config/local.yaml --run-name <이름> cv --all-w`.
- 교란 점검 두 가지: `python -m drowsy.baseline_lgbm --config config/local.yaml --run-name <이름> probes`.
- 속도 특징을 뺀 결과: `python -m drowsy.train --config config/local.yaml --run-name <이름> cv --no-velocity`(신경망)와
  `python -m drowsy.baseline_lgbm --config config/local.yaml --run-name <이름> cv --no-velocity`(LightGBM).
- 순서형 소프트 라벨: `python -m drowsy.train --config config/local.yaml --run-name <이름> cv --ordinal`.
- 약 15 fps 모사 추출에서의 평가: 15 fps 모사 추출(`python -m drowsy.extract --config config/local.yaml --dataset --fps-sim 15`)이
  있으면 위 두 `cv` 명령이 fold 모델을 그 추출로도 평가해 부가 묶음으로 싣는다.
- 전역 조건의 fold별 상수 민감도 점검: `python -m drowsy.baseline_lgbm --config config/local.yaml --run-name <이름> cv --arms
  global --foldwise-global`.
- 팀 수집 차량 영상의 시간당 경고 수: `python -m drowsy.extract --config config/local.yaml --unlabeled` 다음
  `python -m drowsy.evaluate unlabeled --config config/local.yaml --run-name <이름>`. 라벨이 없으므로 정확도가 아니라 경고 수다.

**생성 명령이 없는 행**: Android 기기에서의 추론 지연과 출력 일치. 앱 팀이 잰다.

## 11. 다시 만들기와 변경 기록

```
python -m drowsy.export_onnx --random-init --kind tcn --version 0 --out-dir <폴더>   # v0 (무작위 가중치). 저장소의 export/에 쓰려면 --out-dir을 뺀다
python -m drowsy.train --config config/local.yaml --run-name <이름> cv              # 중첩 교차검증과 리포트
python -m drowsy.train --config config/local.yaml --run-name <이름> final           # 최종 학습과 내보내기(→ export/, rules.json 포함)
python -m drowsy.export_onnx --checkpoint reports/<이름>/final/final_model.pt --spec <내보낸 폴더>/feature_spec_v1.json --version 1 --out-dir <폴더>
```

`config/local.yaml`은 실제 데이터 경로를 적은 `config/default.yaml`의 사본이고 git에 넣지 않는다(README 4.0절).
합성 데이터로 학습한 모델과 `--fast` 모델은 `export/`와 그 아래로 내보내지 못한다. 설정의 `paths.export_dir`이 상대 경로이면
지금 폴더와 저장소 루트 둘 다를 기준으로 보므로, 저장소 밖의 폴더에서 명령을 돌려도 이 보호가 지켜진다. 3차 검증 뒤에는
설정의 `paths.export_dir`이 다른 폴더를 가리켜도(연기 시험용 설정) 저장소의 `export/`를 늘 지킨다.

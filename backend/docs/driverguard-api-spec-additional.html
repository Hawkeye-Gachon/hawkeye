에러 응답 변경

기존 필드(timestamp, status, error, message, path)는 그대로 두고 code 와 fieldErrors 를 추가합니다. 토큰 오류(401)도 같은 형식으로 맞춥니다.

{
  "timestamp": "2026-11-06T07:33:28.287Z",
  "status": 400,
  "error": "Bad Request",
  "code": "VALIDATION_FAILED",
  "message": "입력값을 확인해 주세요.",
  "path": "/api/auth/signup",
  "fieldErrors": [
    { "field": "password", "message": "비밀번호는 8~64자로 입력해 주세요." },
    { "field": "email", "message": "이메일 형식이 올바르지 않습니다." }
  ]
}

fieldErrors 는 입력값 검증 실패일 때만 있고, 그 외에는 생략합니다. 앱은 field 이름으로 해당 입력란 아래에 message 를 표시하면 됩니다.

회원 탈퇴

가이드에는 없는 화면이지만, 계정을 만들 수 있는 앱은 구글 플레이 정책상 계정 삭제 기능이 필요하고 status 에 이미 WITHDRAWN 이 있어 함께 정의합니다. 본인 확인을 위해 비밀번호를 받습니다.

Request Body

필드타입필수설명

서버 처리

  • users.status 를 WITHDRAWN, withdrawn_at 기록. 이메일 유니크가 ACTIVE 사용자에게만 걸려 있어(uq_users_email_active) 같은 이메일로 다시 가입할 수 있습니다.
  • 비밀번호는 auths 의 EMAIL 행 password_hash 로 확인합니다. 확인 후 이 행은 지우는 것을 권장합니다 (탈퇴자의 비밀번호 해시를 남길 이유가 없음).
  • refresh_tokens 전부 삭제. users 행은 남기므로 CASCADE 가 걸리지 않아 직접 지워야 합니다.
  • DELETE FROM drives WHERE user_id = ? — 감지·위치·경유지·시간대 통계는 CASCADE 로 함께 삭제 (보관 기간 정책은 결정 필요).

Drive

업로드 방식: 관찰을 시작할 때 POST /api/drives 로 주행을 등록하고, 관찰 중에는 서버와 통신하지 않습니다. 감지 기록·이동 경로·경유지 추가 기록은 앱이 로컬에 저장해 두었다가 종료할 때 한 번에 POST /api/drives/{driveId}/end 로 올립니다.
주행 상태: IN_PROGRESS 관찰 중 · ENDED 종료 업로드 완료 · ABANDONED 종료 업로드 없이 다음 주행이 시작됨 (나중에 업로드되면 ENDED 로 바뀜). 사용자당 IN_PROGRESS 주행은 1개입니다.
이 방식은 앱의 로컬 저장과 재업로드를 전제로 합니다. 앱은 주행 중 기록을 로컬 DB(Room 등)에 저장하고, 종료 업로드가 실패했거나 앱이 중간에 꺼졌다면 다음 실행 때 다시 올려야 합니다. 서버에서 200 을 받은 뒤에만 로컬 기록을 지웁니다 (시나리오 8).

조회 예시

기간 경계(:from, :to)는 Java 에서 LocalDate.atStartOfDay(ZoneId.of("Asia/Seoul")) 로 만들어 OffsetDateTime 으로 넘기면 인덱스를 그대로 탑니다.

-- 일간 리포트 hourly  (:from = 2026-11-06 00:00+09, :to = 2026-11-07 00:00+09)
SELECT EXTRACT(HOUR FROM hour_start AT TIME ZONE 'Asia/Seoul')::int AS hour,
       SUM(observed_seconds)  AS observed_seconds,
       SUM(inattention_count) AS inattention_count,
       SUM(drowsiness_count)  AS drowsiness_count
FROM drive_hourly_stats
WHERE user_id = :userId AND hour_start >= :from AND hour_start < :to
GROUP BY 1;

-- 주간 통계 daily  (:from = 월요일 00:00+09, :to = 다음 월요일 00:00+09)
SELECT (hour_start AT TIME ZONE 'Asia/Seoul')::date AS date,
       COUNT(DISTINCT drive_id) FILTER (WHERE observed_seconds > 0) AS drive_count,
       SUM(observed_seconds), SUM(inattention_count), SUM(drowsiness_count)
FROM drive_hourly_stats
WHERE user_id = :userId AND hour_start >= :from AND hour_start < :to
GROUP BY 1;

-- 요약의 주행 횟수: 기간과 겹치는 주행 수
SELECT COUNT(DISTINCT drive_id)
FROM drive_hourly_stats
WHERE user_id = :userId AND hour_start >= :from AND hour_start < :to AND observed_seconds > 0;

-- 달력: 주행일
SELECT DISTINCT (hour_start AT TIME ZONE 'Asia/Seoul')::date AS drive_date
FROM drive_hourly_stats
WHERE user_id = :userId AND hour_start >= :monthFrom AND hour_start < :monthTo AND observed_seconds > 0
ORDER BY 1;

-- 가장 최근 주행일 (daily·weekly 에서 날짜 생략 시)
SELECT (MAX(started_at) AT TIME ZONE 'Asia/Seoul')::date
FROM drives
WHERE user_id = :userId AND status = 'ENDED';

참고: 종료 업로드 처리

주행 중에는 서버가 할 일이 없으므로 별도 스케줄러는 필요 없습니다. 아래 계산은 모두 POST /api/drives/{driveId}/end 한 번의 트랜잭션 안에서 처리합니다.

순서단계방식
1잠금·상태 확인SELECT … FOR UPDATE 로 주행 행을 잠금. 이미 ENDED 면 저장하지 않고 기존 리포트 반환 (동시에 두 번 들어온 재전송도 한 번만 처리)
2입력 정리주행 기간 밖 항목, 같은 시각 중복, 정확도 50m 초과 위치, 없는 placeId 를 걸러 skipped 로 집계
3저장drive_events, drive_locations (unnest 한 번에 insert), drive_waypoints (장소명·종류·좌표는 rest_places 에서 복사)
4이동 거리위치를 시각순으로 놓고, 이전 점과의 속도가 70 m/s(약 250 km/h)를 넘는 점은 GPS 튐으로 보고 제외한 뒤 하버사인 거리를 합산
5관찰 시간 · 감지 횟수ended_at − started_at (초), 저장된 이벤트를 종류별로 셈
6시간대 통계시작~종료를 서울 기준 정시 단위로 쪼개 구간별 관찰 시간, 감지 횟수(detected_at 기준), 거리(두 점 중 뒤 점의 시각 기준)를 계산해 drive_hourly_stats 에 저장
7경로 단순화Douglas–Peucker (허용 오차 약 10m). 1,000점이 넘으면 허용 오차를 늘려 다시 수행. route_simplified 에 저장
8쉼터 방문 판정added_at 이후 위치 중 쉼터 좌표 반경 300m 안에 3분 이상 머문 기록이 있으면 visited = TRUE, 처음 들어온 시각을 visited_at
9종료status = 'ENDED', ended_at, 요약값 저장 후 리포트 응답

주행 1건 기준 수천 행 수준이라 요청 안에서 처리해도 충분합니다. ABANDONED 로 남은 주행(로컬 기록까지 사라진 경우)은 리포트에 나오지 않으며, 필요하면 일정 기간 뒤 지우는 정리 작업을 나중에 추가하면 됩니다.
